# izicrm — Финансовая модель

Формальная спецификация всех денежных расчётов. **Единственный источник истины** для P&L.

Правила документа:
- Все величины — точные десятичные числа (`Decimal`). Двоичная плавающая точка не используется нигде.
- Все даты — бизнес-даты (календарная дата в таймзоне пользователя, см. C-8).
- Каждая формула имеет имя функции в коде и ID тестов.

---

## 1. Обозначения

| Символ | Значение |
|---|---|
| `u` | Пользователь |
| `c` | Карта |
| `D` | Бизнес-дата |
| `C(u)` | Множество всех карт пользователя, включая архивные |
| `created_on(c)` | Бизнес-дата создания карты |
| `archived_on(c)` | Бизнес-дата архивирования, либо `null` |
| `kind(c)` | Тип начального баланса: `BALANCE` \| `PROFIT` |
| `reason(c)` | Причина архивирования: `WITHDRAWN` \| `TRANSFERRED` \| `null` |
| `E(c, D)` | Актуальная (не вытесненная) запись баланса карты `c` на дату `D`, если есть |
| `B(c, D)` | LOCF-баланс карты `c` на дату `D` |
| `Cap(u, D)` | Капитал пользователя на дату `D` |
| `F(u, D)` | Чистый внешний поток за дату `D` |
| `⟦P⟧` | Индикатор: 1 если `P` истинно, иначе 0 |

## 2. Аксиомы модели

Аксиомы выведены из требований и определяют границы модели. Нарушение любой из них означает,
что расчёты перестают соответствовать требованиям.

**A-1. Капитал наблюдаем, а не вычисляем.**
Капитал — сумма балансов, введённых пользователем. Система никогда не «досчитывает» баланс.

**A-2. Изменение капитала есть P&L, кроме внешних потоков.**
Любое изменение капитала, не объяснённое внешним потоком, считается прибылью или убытком (§2 требований).

**A-3. Внешние потоки существуют ровно в двух точках жизненного цикла карты** — вход карты в
активное множество и выход из него. Иных источников внешних денег в модели нет.

> Следствие (принятое ограничение, C-7): реальное пополнение карты (например, зарплата) будет
> учтено как прибыль. Требование §2 запрещает спрашивать пользователя о природе изменения,
> поэтому отличить пополнение от прибыли невозможно.

**A-4. Финансовые данные неизменяемы.**
Исправление — это новая запись, вытесняющая предыдущую логически. Физическое удаление отсутствует.

**A-5. Основной P&L считается от капитала, а не от карт.**
Сумма P&L отдельных карт не является P&L пользователя (§1 требований).

## 3. Базовые определения

### 3.1. Актуальная запись баланса

На пару `(c, D)` существует не более одной актуальной записи:

```
E(c, D) = запись из balance_entries с card_id = c, effective_date = D, superseded_at IS NULL
```

Гарантируется частичным unique-индексом (`docs/database.md` §3.3). Исправление за ту же дату
вытесняет предыдущую запись (`superseded_at`, `superseded_by`), физически её сохраняя.

### 3.2. LOCF-баланс — `balanceAsOf(card, date)`

```
B(c, D) = amount(E(c, d*)),  где  d* = max{ d : d ≤ D, E(c, d) существует }
B(c, D) = undefined,          если такого d* нет
```

Смысл: баланс карты на дату `D` — последнее фактически введённое значение на эту дату или ранее.
Это прямая реализация §9: пропущенный день не создаёт записи и не обнуляет баланс.

Так как создание карты всегда пишет запись на `created_on`, для любой карты в scope
`B(c, D)` определён.

### 3.3. Карта в scope — `isInScope(card, date)`

```
InScope(c, D) ⇔ created_on(c) ≤ D  ∧  (archived_on(c) = null ∨ D < archived_on(c))
```

Граница выбрана так, что **в день архивирования карта уже не входит в капитал**. Это делает
депозит и вывод симметричными и корректно обрабатывает создание и архивирование в один день.

### 3.4. Капитал — `capitalAsOf(user, date)`

```
Cap(u, D) = Σ  B(c, D)      по всем c ∈ C(u), где InScope(c, D)
```

`Cap(u, D) = 0`, если ни одна карта не в scope. Суммирование выполняется в `Decimal`
в domain-слое; в SQL суммирование денег запрещено (NFR-11).

## 4. Внешние потоки — производная величина

**Ключевое проектное решение.** Потоки **не хранятся** отдельной таблицей, а **выводятся**
из `cards` и `balance_entries`.

Причина: при хранении потока отдельной строкой исправление начального баланса в день создания
карты рассинхронизирует поток и баланс. Пример — пользователь создал карту на `30 000` (опечатка)
и сразу исправил на `3 000`:

| Модель потоков | Депозит | Капитал | P&L | Верно? |
|---|---|---|---|---|
| Хранимый | 30 000 | 3 000 | **−27 000** | нет, фантомный убыток |
| Производный | 3 000 | 3 000 | **0** | да |

Производная модель самосогласована по построению: любое исправление баланса автоматически
исправляет поток.

### 4.1. Депозит — `deriveDeposit(card)`

```
Deposit(c) = B(c, created_on(c))   если kind(c) = BALANCE
           = 0                     если kind(c) = PROFIT
дата потока = created_on(c)
```

`kind = PROFIT` не создаёт потока — поэтому начальный баланс автоматически попадает в прибыль (FR-2.4).

### 4.2. Вывод — `deriveWithdrawal(card)`

```
Withdrawal(c) = B(c, archived_on(c))   если archived_on(c) ≠ null ∧ reason(c) = WITHDRAWN
              = 0                       если reason(c) = TRANSFERRED  ∨  archived_on(c) = null
дата потока = archived_on(c)
```

`TRANSFERRED` не создаёт потока, потому что остаток в той же транзакции добавлен к балансу
карты-получателя за ту же дату — капитал не изменился (C-3).

### 4.3. Чистый поток за период — `netFlow(user, from, to)`

```
NetFlow(u, [A, B]) = Σ Deposit(c) · ⟦A ≤ created_on(c) ≤ B⟧
                   − Σ Withdrawal(c) · ⟦A ≤ archived_on(c) ≤ B⟧
```

Знак: ввод денег в систему положителен, вывод отрицателен.

## 5. Главная формула — `periodPnl(user, from, to)`

Единственная функция расчёта прибыли в системе (FR-5.9, NFR-8).

```
PnL(u, A, B) = Cap(u, B) − Cap(u, A − 1 день) − NetFlow(u, [A, B])
```

Читается так: изменение капитала за период минус деньги, которые пришли извне.

**Соглашение о границах.** База отсчёта — закрытие дня, предшествующего периоду (`A − 1`).
Потоки учитываются за даты `[A, B]` включительно. Это соглашение делает соседние периоды
непересекающимися и обеспечивает аддитивность (§6).

### 5.1. Доходность за период — `periodReturn(user, from, to)`

```
Base(u, A)      = Cap(u, A − 1 день)
Return(u, A, B) = PnL(u, A, B) / Base(u, A) × 100     если Base > 0
                = НЕ ОПРЕДЕЛЕНА («—»)                 если Base ≤ 0
```

Возвращается размеченный тип, а не число:

```ts
type PercentResult =
  | { defined: true; value: Decimal }
  | { defined: false; reason: 'ZERO_BASE' | 'NEGATIVE_BASE' | 'NO_PREVIOUS_DATA' };
```

Тип делает невозможным случайное отображение `0%` вместо `—` (C-2).

### 5.2. Дневной P&L — `dailyPnl(user, date)`

```
prev(u, D) = max{ d : d < D, ∃ c ∈ C(u): E(c, d) существует }

DailyPnL(u, D)    = PnL(u, prev + 1 день, D)
                  = Cap(u, D) − Cap(u, prev) − NetFlow(u, (prev, D])
DailyReturn(u, D) = DailyPnL / Cap(u, prev) × 100      если Cap(u, prev) > 0
periodDays(u, D)  = D − prev(u, D)                     в днях
```

Если `prev(u, D)` не существует (первое обновление в истории) — P&L и процент не рассчитываются,
выводится `—` (FR-5.6).

**Пропущенные дни (§9).** `prev` — предыдущая дата с фактической записью, а не `D − 1`.
Синтетические записи не создаются, нулевая прибыль не подставляется. P&L считается за фактический
интервал; `periodDays > 1` отражается в UI подписью «за N дней» (C-14).

### 5.3. Месячный P&L — `monthlyPnl(user, year, month)`

```
S = первое число месяца
E = min(последний день месяца, последняя дата с записью)

MonthlyPnL(u, M)    = Cap(u, E) − Cap(u, S − 1 день) − NetFlow(u, [S, E])
MonthlyReturn(u, M) = MonthlyPnL / Cap(u, S − 1) × 100     если база > 0
```

База — закрытие последнего дня предыдущего месяца (C-4). Именно это устраняет ложную прибыль
при добавлении карты в середине месяца: депозит попадает в `NetFlow` и вычитается.

### 5.4. P&L за всё время — `allTimePnl(user)`

```
TotalDeposits(u)    = Σ Deposit(c)      по всем c ∈ C(u)
TotalWithdrawals(u) = Σ Withdrawal(c)   по всем c ∈ C(u)

TotalPnL(u)    = Cap(u, today) − TotalDeposits(u) + TotalWithdrawals(u)
TotalReturn(u) = TotalPnL / TotalDeposits × 100     если TotalDeposits > 0, иначе «—»
```

Вытекает из главной формулы: `Cap(u, firstDate − 1) = 0`. База — фактически внесённые деньги (C-15).

### 5.5. Modified Dietz — `modifiedDietzReturn(user, from, to)`

Дополнительная метрика для Excel. Учитывает, что средства, внесённые в середине периода,
работали не весь период.

```
T   = число дней в [A, B]
tᵢ  = номер дня потока i внутри периода, 1-based
wᵢ  = (T − tᵢ + 1) / T
MDB = Cap(u, A − 1) + Σ wᵢ · Fᵢ          (Fᵢ — знаковый поток)
MD  = PnL(u, A, B) / MDB × 100           если MDB > 0
```

Зачем: простая доходность завышает результат при крупном пополнении в середине периода.
На примере §6 требований: простая = `5.00%`, Modified Dietz = `4.29%`. В Telegram выводится
простая доходность (как в требованиях), в Excel — обе.

### 5.6. Изменение баланса карты — `cardBalanceChange(card, date)`

**Информационная метрика. Не прибыль.** Отдельно от P&L (A-5, FR-5.4).

```
CardChange(c, D)  = B(c, D) − B(c, prev(u, D))         если InScope(c, prev(u, D))
                  = НЕ ОПРЕДЕЛЕНО («новая карта»)       иначе
CardChangePct(c, D) = CardChange / B(c, prev) × 100     если B(c, prev) > 0
```

**База — `prev(u, D)` пользователя, а не дата последнего обновления самой карты.** Это даёт
свойство сходимости: для карт, находившихся в scope на обеих датах,

```
Σ CardChange(c, D) = Cap(u, D) − Cap(u, prev)
```

то есть строки карт на главном экране сходятся с общим изменением капитала. Карта, не обновлённая
в этот день, честно показывает `+0 ₽ (0.00%)` — как `Тинькофф` в макете §10.

**Именование обязательно.** В коде и отчётах — `balanceChange`, а не `profit`. Причина: при
переводе между картами эта метрика показывает движение, а не результат.
`Σ CardChange ≠ TotalPnL` в общем случае, и это не ошибка (§1 требований).

## 6. Теоремы и инварианты

Каждая теорема — исполняемый тест. Это защита от регрессий в финансовой логике.

### T-1. Нейтральность перевода между своими картами

> Если `Cap(u, D) = Cap(u, prev)` и `NetFlow = 0`, то `DailyPnL(u, D) = 0` при любых изменениях
> отдельных карт.

Доказательство: подстановка в §5.2. Тривиально, но это главное требование §1.

Пример: `10 000 + 20 000 = 30 000` → `5 000 + 25 000 = 30 000` ⟹ `PnL = 0`.
Property-тест: генерируем перестановку сумм с сохранением суммы — P&L всегда 0.

### T-2. P&L-нейтральность создания карты

> Создание карты с `kind = BALANCE` и суммой `X` не меняет `PnL` за любой период.

Доказательство: `Cap` растёт на `X`, `NetFlow` растёт на `X`, разность неизменна. ∎

### T-3. P&L-нейтральность архивирования

> Архивирование карты с остатком `X` не меняет `PnL` ни при `WITHDRAWN`, ни при `TRANSFERRED`.

Доказательство. `WITHDRAWN`: `Cap` падает на `X`, `NetFlow` уменьшается на `X`, разность
`Cap − NetFlow` неизменна. `TRANSFERRED`: `X` переносится на карту-получателя в той же транзакции,
`Cap` не меняется, потока нет. ∎

### T-4. Аддитивность рублёвого P&L (телескопирование)

> Для последовательных дат обновления `d₀ = A − 1 < d₁ < … < dₙ = B`:
> `Σᵢ DailyPnL(dᵢ) = PnL(A, B)`

Доказательство:
```
Σᵢ [Cap(dᵢ) − Cap(dᵢ₋₁) − NetFlow(dᵢ₋₁, dᵢ]]
  = Cap(dₙ) − Cap(d₀) − NetFlow(d₀, dₙ]        (телескопирование)
  = PnL(A, B)                                   ∎
```

Следствие: сумма дневных P&L за месяц точно равна месячному P&L. Проверено численно.

### T-5. Проценты не аддитивны

> `Σ DailyReturn ≠ MonthlyReturn` в общем случае.

Поэтому проценты никогда не суммируются. Корректная композиция — time-weighted return
`Π(1 + rᵢ) − 1`; выводится только в Excel как отдельная метрика (C-16).

### T-6. Согласованность отображаемого капитала

> `Σ` балансов активных карт на главном экране `= Cap(u, D)`.

Защищает от расхождения макета §10 (`39 600 ≠ 116 000`, см. C-5).

### T-7. Независимость от пропущенных дней

> Вставка или удаление дней без обновлений не меняет `PnL` за период, содержащий эти дни.

Прямое следствие LOCF. Реализация §9.

### T-8. Детерминированность

> Один и тот же набор данных всегда даёт побитово идентичный результат.

Никаких `Date.now()` внутри domain-слоя: текущая дата передаётся параметром.

## 7. Разобранные примеры

### П-1. Перемещение между своими картами (§1 требований)

| | Сбер1 | Сбер2 | Капитал |
|---|---|---|---|
| Вчера | 10 000 | 20 000 | 30 000 |
| Сегодня | 5 000 | 25 000 | 30 000 |

`PnL = 30 000 − 30 000 − 0 = 0 ₽`, `Return = 0.00%`.
Изменения карт: `−5 000` и `+5 000`; их сумма 0 — согласуется с T-1 и §5.6.

### П-2. Новая карта в середине месяца (§6 требований)

| Дата | Событие | Капитал | Поток |
|---|---|---|---|
| 31 июля | закрытие | 100 000 | — |
| 15 августа | создана карта 30 000, `BALANCE` | 130 000 | +30 000 |
| 20 августа | обновление | 135 000 | — |

```
MonthlyPnL = 135 000 − 100 000 − 30 000 = 5 000 ₽     ✓ ожидание требований
Return     = 5 000 / 100 000 = 5.00%
Modified Dietz = 5 000 / (100 000 + 0.5484 × 30 000) = 4.29%
```

### П-3. То же, но выбрано «Это прибыль»

Поток не создаётся: `PnL = 135 000 − 100 000 − 0 = 35 000 ₽`.
Начальный баланс полностью попал в прибыль, как требует §3.

### П-4. Архивирование: вывод денег

Вчера `Сбер1 = 10 000`, `Сбер2 = 20 000`. Сегодня `Сбер2` архивирована, `reason = WITHDRAWN`.

```
Cap(today) = 10 000;  Withdrawal = 20 000;  NetFlow = −20 000
PnL = 10 000 − 30 000 − (−20 000) = 0 ₽      ✓
```

### П-5. Архивирование: перевод на другую карту

Остаток `20 000` переносится на `Сбер1` в той же транзакции: `Сбер1 = 30 000`, потока нет.

```
PnL = 30 000 − 30 000 − 0 = 0 ₽              ✓
```

Без механизма C-3 этот сценарий давал бы `+20 000 ₽` фантомной прибыли.

### П-6. Пропущенные дни

Обновления: 10 августа → 100 000, 14 августа → 103 000. 11–13 августа записей нет.

```
prev(14 авг) = 10 авг;  periodDays = 4
DailyPnL = 103 000 − 100 000 = 3 000 ₽;  Return = 3.00%
```
UI: `+3 000 ₽ (+3.00%) · за 4 дня`. Синтетические нули не создаются (§9).

### П-7. Первая карта с типом «Это прибыль»

Создана первая карта на `10 000`, `kind = PROFIT`. `TotalDeposits = 0`.

```
TotalPnL    = 10 000 − 0 + 0 = 10 000 ₽
TotalReturn = 10 000 / 0 → НЕ ОПРЕДЕЛЕНА → «—»
```
Математически доходность бесконечна. Показывается `—`, не `0%` и не ошибка (C-2).

### П-8. Исправление опечатки в день создания

Создана карта `30 000` (`BALANCE`), тут же исправлена на `3 000`.
Депозит производный ⟹ `Deposit = 3 000`, `Cap = 3 000`, `PnL = 0 ₽`. См. §4.

## 8. Денежная арифметика и округление

| Правило | Значение |
|---|---|
| Тип хранения | `NUMERIC(20,2)`, диапазон до `999 999 999 999 999 999.99` |
| Тип в коде | `Money` — branded-тип над `Decimal`, шкала строго 2 |
| Точность вычислений | `Decimal` с precision 34 (decimal128-класс) |
| Округление денег | `ROUND_HALF_UP` до 2 знаков, только на границе вывода/записи |
| Округление процентов | `ROUND_HALF_UP` до 2 знаков, только при отображении |
| Промежуточные значения | Не округляются. Округление — последняя операция |
| Ввод | > 2 знаков после запятой отклоняется с ошибкой, без молчаливого округления (C-12) |
| Деление | Только при расчёте процентов. Деньги никогда не делятся на деньги с записью результата |

**Запрещено:** `number` для денег · `parseFloat` · `Number()` над `Decimal` · `Math.round`
· `toFixed` для расчётов · JSON-числа для денег (в `JSONB` и FSM-состоянии деньги — строки)
· `SUM()` по деньгам в SQL (NFR-11) · неявное `Decimal → number`.

Форматирование: `116 000 ₽` (узкий пробел U+202F как разделитель разрядов), копейки
опускаются при `.00`, знак всегда явный для дельт (`+1 200 ₽`, `−450 ₽`), для процентов
`+1.05%`. Отсутствующее значение — `—` (em dash).
