# izicrm — Финансовая модель

Формальная спецификация всех денежных расчётов. **Единственный источник истины** для P&L.

Правила документа:
- Все величины — точные десятичные числа (`Decimal`). Двоичная плавающая точка не используется нигде.
- Все даты — бизнес-даты (календарная дата в таймзоне пользователя, см. C-8).
- Каждая формула имеет имя функции в коде и ID тестов.

---

## 1. Обозначения

| Символ | Значение |
|---|---|
| `u` | Пользователь |
| `c` | Карта |
| `D` | Бизнес-дата |
| `C(u)` | Множество всех карт пользователя, включая архивные |
| `created_on(c)` | Бизнес-дата создания карты |
| `archived_on(c)` | Бизнес-дата архивирования, либо `null` |
| `frozen_on(c)` | Бизнес-дата текущей заморозки, либо `null`. История заморозок не ведётся (C-27) |
| `reason(c)` | Причина архивирования: `WITHDRAWN` \| `TRANSFERRED` \| `LOST` \| `null` |
| `E(c, D)` | Актуальная (не вытесненная) запись баланса карты `c` на дату `D`, если есть |
| `I(c, D)` | `capital_in` записи — внешний ввод, отнесённый к наблюдению |
| `O(c, D)` | `capital_out` записи — вывод (трата) без удаления карты |
| `B(c, D)` | LOCF-баланс карты `c` на дату `D` |
| `Cap(u, D)` | Капитал пользователя на дату `D` (оборот + заморожено) |
| `WorkCap(u, D)` | Капитал карт в обороте на дату `D` |
| `FrozenCap(u, D)` | Капитал замороженных карт на дату `D` |
| `F(u, D)` | Чистый внешний поток за дату `D` |
| `⟦P⟧` | Индикатор: 1 если `P` истинно, иначе 0 |

## 2. Аксиомы модели

Аксиомы выведены из требований и определяют границы модели. Нарушение любой из них означает,
что расчёты перестают соответствовать требованиям.

**A-1. Капитал наблюдаем, а не вычисляем.**
Капитал — сумма балансов, введённых пользователем. Система никогда не «досчитывает» баланс.

**A-2. Изменение капитала есть P&L, кроме внешних потоков.**
Любое изменение капитала, не объяснённое внешним потоком, считается прибылью или убытком.
Практически прибыль появляется только при обновлении балансов: создание и пополнение —
потоки, не P&L.

**A-3. Внешние потоки — любое движение денег через границу учёта.**
Три источника:

1. Создание материала: начальный баланс = депозит (`capital_in = amount`).
2. Пополнение существующего материала: разница `Y − текущий` = депозит (C-26).
3. Трата без удаления: разница `текущий − Y` = вывод (C-30).
4. Выход карты из учёта с причиной `WITHDRAWN`: остаток = вывод.

Заморозка и разморозка потока не создают: деньги остаются в капитале (C-27).
Перевод при архивировании потока не создаёт: деньги остаются на другой карте.

> Прежнее следствие C-7 («зарплата на карте = прибыль, потому что спросить нечем»)
> отменено 24.08.2026. Намерение различают две кнопки: «Пополнить» и «Обновить».

**A-4. Финансовые данные неизменяемы.**
Исправление — это новая запись, вытесняющая предыдущую логически. Физическое удаление отсутствует.

**A-5. Основной P&L считается от капитала, а не от карт.**
Сумма P&L отдельных карт не является P&L пользователя (§1 требований).

**A-6. Заморозка не выводит деньги.**
Замороженный материал остаётся в `Cap`. «В работе» и «заморожено» — разрез одного капитала,
а не два разных учёта. На экране: `В работе + Заморожено = Всего`.

## 3. Базовые определения

### 3.1. Актуальная запись баланса

На пару `(c, D)` существует не более одной актуальной записи:

```
E(c, D) = запись из balance_entries с card_id = c, effective_date = D, superseded_at IS NULL
```

Гарантируется частичным unique-индексом (`docs/database.md` §3.3). Исправление за ту же дату
вытесняет предыдущую запись (`superseded_at`, `superseded_by`), физически её сохраняя.

### 3.2. LOCF-баланс — `balanceAsOf(card, date)`

```
B(c, D) = amount(E(c, d*)),  где  d* = max{ d : d ≤ D, E(c, d) существует }
B(c, D) = undefined,          если такого d* нет
```

Смысл: баланс карты на дату `D` — последнее фактически введённое значение на эту дату или ранее.
Это прямая реализация §9: пропущенный день не создаёт записи и не обнуляет баланс.

Так как создание карты всегда пишет запись на `created_on`, для любой карты в scope
`B(c, D)` определён.

### 3.3. Карта в scope — `isInScope(card, date)`

```
InScope(c, D) ⇔ created_on(c) ≤ D  ∧  (archived_on(c) = null ∨ D < archived_on(c))
```

Граница выбрана так, что **в день архивирования карта уже не входит в капитал**. Это делает
депозит и вывод симметричными и корректно обрабатывает создание и архивирование в один день.

Заморозка scope не меняет. Для разреза оборота:

```
IsFrozen(c, D) ⇔ frozen_on(c) ≠ null
InWorking(c, D) ⇔ InScope(c, D) ∧ ¬IsFrozen(c)
```

`IsFrozen` — текущий флаг, не функция от `D`. Ретроспектива «было ли заморожено на дату
в прошлом» в v1 не восстанавливается (C-27). Формулы капитала на прошлую дату используют
полный `InScope`; разрез оборот/заморожено на главном экране — только на «сегодня».

### 3.4. Капитал — `capitalAsOf(user, date)`

```
Cap(u, D)       = Σ  B(c, D)      по всем c ∈ C(u), где InScope(c, D)
WorkCap(u, D)   = Σ  B(c, D)      по всем c ∈ C(u), где InWorking(c, D)
FrozenCap(u, D) = Σ  B(c, D)      по всем c ∈ C(u), где InScope(c, D) ∧ IsFrozen(c)
```

`Cap(u, D) = 0`, если ни одна карта не в scope. На текущую дату
`Cap = WorkCap + FrozenCap` (T-6). Суммирование выполняется в `Decimal`
в domain-слое; в SQL суммирование денег запрещено (NFR-11).

## 4. Внешние потоки — производная величина

**Ключевое проектное решение.** Потоки **не хранятся** отдельной таблицей. Депозиты и траты
читаются с полей `capital_in` / `capital_out` актуальной записи баланса. Выводы при
архивировании `WITHDRAWN` выводятся из остатка карты.

Причина та же, что раньше: отдельная строка потока рассинхронизируется с исправленным
балансом. Пример — пользователь создал карту на `30 000` (опечатка) и сразу исправил
на `3 000`. Исправление вытесняет запись вместе с `capital_in`:

| Модель потоков | Депозит | Капитал | P&L | Верно? |
|---|---|---|---|---|
| Хранимый отдельно | 30 000 | 3 000 | **−27 000** | нет, фантомный убыток |
| На записи (`capital_in`) | 3 000 | 3 000 | **0** | да |

Производная модель самосогласована по построению: любое исправление баланса автоматически
исправляет поток, потому что `capital_in` живёт на той же вытесняемой строке (C-26).

### 4.1. Депозит — `deriveDeposit(entry)` / `netDeposits(user, from, to)`

```
Deposit(c, D) = I(c, D)            если E(c, D) существует
              = 0                  иначе

NetDeposits(u, [A, B]) = Σ I(c, d)   по всем актуальным записям с A ≤ d ≤ B
```

`I(c, D)` — поле `capital_in` актуальной записи. Как оно появляется (C-26):

| Операция | Поток на итоговой записи за день |
|---|---|
| Создание материала с балансом `X` | `capital_in = X` |
| Обновление баланса | потоки без изменения; `0`/`0`, если это первая запись за день |
| Пополнение, новый баланс `Y >` текущего | `capital_in += Y − текущий` |
| Трата, новый баланс `Y <` текущего | `capital_out += текущий − Y` |

Типа `PROFIT` нет (C-29): стартовый баланс всегда депозит.

### 4.2. Вывод — `deriveWithdrawal(card)`

```
Withdrawal(c) = B(c, archived_on(c))   если archived_on(c) ≠ null ∧ reason(c) = WITHDRAWN
              = 0                       если reason(c) ∈ {TRANSFERRED, LOST} ∨ archived_on(c) = null
дата потока = archived_on(c)
```

`TRANSFERRED` не создаёт потока, потому что остаток в той же транзакции добавлен к балансу
карты-получателя за ту же дату — капитал не изменился (C-3).

`LOST` не создаёт потока по противоположной причине: капитал падает на остаток, и это падение
**и есть** убыток. Записать здесь поток означало бы объявить деньги выведенными, то есть скрыть
убыток от расчёта. Три причины архивирования различаются ровно этим (C-17):

| Причина | Что было с деньгами | Капитал | Поток | Вклад в P&L |
|---|---|---|---|---|
| `TRANSFERRED` | переведены на свою же карту | не меняется | нет | `0` |
| `WITHDRAWN` | выведены из учёта (сняты, потрачены) | падает на `X` | `−X` | `0` |
| `LOST` | потеряны | падает на `X` | нет | `−X` |

Различие `WITHDRAWN` и `LOST` — не техническое, а смысловое, и решить его за пользователя нельзя:
одно и то же уменьшение капитала в первом случае прибыль не затрагивает, во втором уменьшает её
на всю сумму. Поэтому вопрос задаётся явно, а формулировки кнопок называют последствие
(`docs/telegram-flows.md` §4).

### 4.3. Чистый поток за период — `netFlow(user, from, to)`

```
NetFlow(u, [A, B]) = Σ I(c, d) − Σ O(c, d)     по актуальным записям с A ≤ d ≤ B
                   − Σ Withdrawal(c) · ⟦A ≤ archived_on(c) ≤ B⟧
```

Знак: ввод денег в систему положителен, вывод отрицателен.

## 5. Главная формула — `periodPnl(user, from, to)`

Единственная функция расчёта прибыли в системе (FR-5.9, NFR-8).

```
PnL(u, A, B) = Cap(u, B) − Cap(u, A − 1 день) − NetFlow(u, [A, B])
```

Читается так: изменение капитала за период минус деньги, которые пришли извне.

**Соглашение о границах.** База отсчёта — закрытие дня, предшествующего периоду (`A − 1`).
Потоки учитываются за даты `[A, B]` включительно. Это соглашение делает соседние периоды
непересекающимися и обеспечивает аддитивность (§6).

### 5.1. Доходность за период — `periodReturn(user, from, to)`

```
Base(u, A)      = Cap(u, A − 1 день)
Return(u, A, B) = PnL(u, A, B) / Base(u, A) × 100     если Base > 0
                = НЕ ОПРЕДЕЛЕНА («—»)                 если Base ≤ 0
```

Возвращается размеченный тип, а не число:

```ts
type PercentResult =
  | { defined: true; value: Decimal }
  | { defined: false; reason: 'ZERO_BASE' | 'NEGATIVE_BASE' | 'NO_PREVIOUS_DATA' };
```

Тип делает невозможным случайное отображение `0%` вместо `—` (C-2).

### 5.2. Дневной P&L — `dailyPnl(user, date)`

```
prev(u, D) = max{ d : d < D, ∃ c ∈ C(u): E(c, d) существует }

DailyPnL(u, D)    = PnL(u, prev + 1 день, D)
                  = Cap(u, D) − Cap(u, prev) − NetFlow(u, (prev, D])
DailyReturn(u, D) = DailyPnL / Cap(u, prev) × 100      если Cap(u, prev) > 0
periodDays(u, D)  = D − prev(u, D)                     в днях
```

Если `prev(u, D)` не существует (первое обновление в истории) — P&L и процент не рассчитываются,
выводится `—` (FR-5.6).

**Пропущенные дни (§9).** `prev` — предыдущая дата с фактической записью, а не `D − 1`.
Синтетические записи не создаются, нулевая прибыль не подставляется. P&L считается за фактический
интервал; `periodDays > 1` отражается в UI подписью «за N дней» (C-14).

### 5.3. Месячный P&L — `monthlyPnl(user, year, month)`

```
S = первое число месяца
E = min(последний день месяца, последняя дата с записью)

MonthlyPnL(u, M)    = Cap(u, E) − Cap(u, S − 1 день) − NetFlow(u, [S, E])
MonthlyReturn(u, M) = MonthlyPnL / Cap(u, S − 1) × 100     если база > 0
```

База — закрытие последнего дня предыдущего месяца (C-4). Именно это устраняет ложную прибыль
при добавлении карты или пополнении в середине месяца: депозит попадает в `NetFlow` и вычитается.

### 5.4. P&L за всё время — `allTimePnl(user)`

```
TotalDeposits(u)    = Σ I(c, d)         по всем актуальным записям
TotalWithdrawals(u) = Σ Withdrawal(c)   по всем c ∈ C(u)

TotalPnL(u)    = Cap(u, today) − TotalDeposits(u) + TotalWithdrawals(u)
TotalReturn(u) = TotalPnL / TotalDeposits × 100     если TotalDeposits > 0, иначе «—»
```

Вытекает из главной формулы: `Cap(u, firstDate − 1) = 0`. База — фактически внесённые деньги (C-15).

### 5.5. Modified Dietz — `modifiedDietzReturn(user, from, to)`

Дополнительная метрика для Excel. Учитывает, что средства, внесённые в середине периода,
работали не весь период.

```
T   = число дней в [A, B]
tᵢ  = номер дня потока i внутри периода, 1-based
wᵢ  = (T − tᵢ + 1) / T
MDB = Cap(u, A − 1) + Σ wᵢ · Fᵢ          (Fᵢ — знаковый поток)
MD  = PnL(u, A, B) / MDB × 100           если MDB > 0
```

Зачем: простая доходность завышает результат при крупном пополнении в середине периода.
На примере §6 требований: простая = `5.00%`, Modified Dietz = `4.29%`. В Telegram выводится
простая доходность (как в требованиях), в Excel — обе.

### 5.6. Изменение баланса карты — `cardBalanceChange(card, date)`

**Информационная метрика. Не прибыль.** Отдельно от P&L (A-5, FR-5.4).

```
CardChange(c, D)  = B(c, D) − B(c, prev(u, D))         если InScope(c, prev(u, D))
                  = НЕ ОПРЕДЕЛЕНО («новая карта»)       иначе
CardChangePct(c, D) = CardChange / B(c, prev) × 100     если B(c, prev) > 0
```

**База — `prev(u, D)` пользователя, а не дата последнего обновления самой карты.** Карта,
не обновлённая в этот день, честно показывает `+0 ₽ (0.00%)` — как `Тинькофф` в макете §10.

Свойство сходимости. `CardChange` определён только для карт, которые были в scope на обеих
датах. Карта, созданная после `prev`, в сумму не входит (`«новая карта»`); карта, архивированная
в интервале, на главном экране уже не показывается. Поэтому

```
Cap(u, D) − Cap(u, prev)
  = Σ CardChange(c, D)
  + Σ B(c, D)          по картам, вошедшим в scope на D
  − Σ B(c, prev)       по картам, вышедшим из scope к D
```

Это тождество, а не приближение: оно следует из определения капитала и проверяется PT-08
на случайных историях, включая создание и архивирование.

Следствие для прибыли. Подставляя главную формулу и раскрывая `NetFlow` по §4
(депозит = `capital_in` записей периода; вывод только у `WITHDRAWN`):

```
PnL(u, prev+1, D)
  = Σ CardChange(c, D)
  − Σ B(c, prev)       по картам, архивированным в интервале с reason ∈ {TRANSFERRED, LOST}
  − Σ I(c, d)          по пополнениям карт, которые уже были в scope на prev
```

Создание материала равенство **сохраняет**: рост капитала ровно равен `capital_in`.
Пополнение уже существовавшей карты — нет: `CardChange` включает `Δ`, а прибыль не должна.
Удаление с `WITHDRAWN` равенство сохраняет. Пример главного экрана в `telegram-flows.md` §1.1 —
день без создания, пополнения, перевода и потери, поэтому числа там сходятся.

**Именование обязательно.** В коде и отчётах — `balanceChange`, а не `profit`. Причина: при
переводе между картами эта метрика показывает движение, а не результат.
`Σ CardChange ≠ TotalPnL` в общем случае, и это не ошибка (§1 требований).

## 6. Теоремы и инварианты

Каждая теорема — исполняемый тест. Это защита от регрессий в финансовой логике.

### T-1. Нейтральность перевода между своими картами

> Если `Cap(u, D) = Cap(u, prev)` и `NetFlow = 0`, то `DailyPnL(u, D) = 0` при любых изменениях
> отдельных карт.

Доказательство: подстановка в §5.2. Тривиально, но это главное требование §1.

Пример: `10 000 + 20 000 = 30 000` → `5 000 + 25 000 = 30 000` ⟹ `PnL = 0`.
Property-тест: генерируем перестановку сумм с сохранением суммы — P&L всегда 0.

### T-2. P&L-нейтральность создания карты

> Создание карты с суммой `X` не меняет `PnL` за любой период.

Доказательство: `Cap` растёт на `X`, `NetFlow` растёт на `X` (`capital_in = X`), разность неизменна. ∎

### T-10. P&L-нейтральность пополнения

> Пополнение карты (новый баланс `Y >` текущего) не меняет `PnL` за любой период, содержащий эту дату.

Доказательство: `Δ = Y − текущий`, `Cap` растёт на `Δ`, `capital_in` растёт на `Δ`,
разность неизменна. Композиция с обновлением в тот же день: если баланс сначала стал
`Y₀`, затем пополнили до `Y₁`, то `PnL = Y₁ − Cap(prev) − (capital_in_update + (Y₁−Y₀))` —
добавка сокращается, прибыль обновления остаётся. ∎

### T-12. P&L-нейтральность траты

> Трата (новый баланс `Y <` текущего) не меняет `PnL` за любой период, содержащий эту дату.

Доказательство: `Δ = текущий − Y`, `Cap` падает на `Δ`, `capital_out` растёт на `Δ`,
`NetFlow` уменьшается на `Δ`, разность `Cap − NetFlow` неизменна. ∎

Если вместо траты нажать «обновить» и ввести то же `Y`, это будет убыток `Δ`. Намерение
различает кнопка.

Две границы property-теста: пополнение не даёт `+Δ` прибыли и не даёт `−Δ` убытка.

### T-11. Нейтральность заморозки и разморозки

> Заморозка и разморозка карты не меняют `Cap(u, D)` и `PnL` ни за какой период.

Доказательство: множество `InScope` не меняется, балансы не меняются, потока нет.
`WorkCap` и `FrozenCap` перекладываются, сумма — нет. ∎

### T-3. P&L-нейтральность архивирования

> Архивирование карты с остатком `X` не меняет `PnL` ни при `WITHDRAWN`, ни при `TRANSFERRED`.

Доказательство. `WITHDRAWN`: `Cap` падает на `X`, `NetFlow` уменьшается на `X`, разность
`Cap − NetFlow` неизменна. `TRANSFERRED`: `X` переносится на карту-получателя в той же транзакции,
`Cap` не меняется, потока нет. ∎

Теорема **не** распространяется на `LOST` — это единственная причина архивирования, меняющая
прибыль, см. T-9.

### T-9. Точность убытка при `LOST`

> Архивирование карты с остатком `X` и причиной `LOST` уменьшает `PnL` ровно на `X`,
> ни больше ни меньше.

Доказательство. `Cap` падает на `X`, поток не создаётся, значит
`PnL' = (Cap − X) − Cap(A−1) − NetFlow = PnL − X`. ∎

Две границы, которые проверяет property-тест:

- **Ровно `X`, не больше.** Если бы при `LOST` дополнительно записывался поток `−X`, убыток
 удвоился бы до `2X`. Тест ловит именно такую ошибку реализации.
- **Ровно `X`, не меньше.** Если бы поток записывался как при `WITHDRAWN`, убыток обнулился бы.

Инвариант, связывающий все три причины: для одной и той же карты с остатком `X`
`PnL(TRANSFERRED) = PnL(WITHDRAWN) = PnL(LOST) + X`. Он проверяется одним тестом на трёх
прогонах с идентичными входными данными и разной причиной — так расхождение в реализации
любой из ветвей обнаруживается сразу.

### T-4. Аддитивность рублёвого P&L (телескопирование)

> Для последовательных дат обновления `d₀ = A − 1 < d₁ < … < dₙ = B`:
> `Σᵢ DailyPnL(dᵢ) = PnL(A, B)`

Доказательство:
```
Σᵢ [Cap(dᵢ) − Cap(dᵢ₋₁) − NetFlow(dᵢ₋₁, dᵢ]]
  = Cap(dₙ) − Cap(d₀) − NetFlow(d₀, dₙ]        (телескопирование)
  = PnL(A, B)                                   ∎
```

Следствие: сумма дневных P&L за месяц точно равна месячному P&L. Проверено численно.

### T-5. Проценты не аддитивны

> `Σ DailyReturn ≠ MonthlyReturn` в общем случае.

Поэтому проценты никогда не суммируются. Корректная композиция — time-weighted return
`Π(1 + rᵢ) − 1`; выводится только в Excel как отдельная метрика (C-16).

### T-6. Согласованность отображаемого капитала

> На главном экране `Σ` балансов в работе `= WorkCap`, `Σ` замороженных `= FrozenCap`,
> и `WorkCap + FrozenCap = Cap(u, D)` («Всего»).

Защищает от расхождения макета §10 (`39 600 ≠ 116 000`, см. C-5) и от «потерянных»
замороженных сумм.

### T-7. Независимость от пропущенных дней

> Вставка или удаление дней без обновлений не меняет `PnL` за период, содержащий эти дни.

Прямое следствие LOCF. Реализация §9.

### T-8. Детерминированность

> Один и тот же набор данных всегда даёт побитово идентичный результат.

Никаких `Date.now()` внутри domain-слоя: текущая дата передаётся параметром.

## 7. Разобранные примеры

### П-1. Перемещение между своими картами (§1 требований)

| | Сбер1 | Сбер2 | Капитал |
|---|---|---|---|
| Вчера | 10 000 | 20 000 | 30 000 |
| Сегодня | 5 000 | 25 000 | 30 000 |

`PnL = 30 000 − 30 000 − 0 = 0 ₽`, `Return = 0.00%`.
Изменения карт: `−5 000` и `+5 000`; их сумма 0 — согласуется с T-1 и §5.6.

### П-2. Новая карта в середине месяца

| Дата | Событие | Капитал | Поток |
|---|---|---|---|
| 31 июля | закрытие | 100 000 | — |
| 15 августа | создана карта 30 000 | 130 000 | +30 000 |
| 20 августа | обновление | 135 000 | — |

```
MonthlyPnL = 135 000 − 100 000 − 30 000 = 5 000 ₽     ✓
Return     = 5 000 / 100 000 = 5.00%
Modified Dietz = 5 000 / (100 000 + 0.5484 × 30 000) = 4.29%
```

### П-3. Пополнение существующей карты в середине месяца

Те же 31 июля = 100 000. 15 августа карту не создают, а пополняют: вводят новый баланс
130 000 (было 100 000).

```
MonthlyPnL = 135 000 − 100 000 − 30 000 = 5 000 ₽     ✓ как П-2
```

Если вместо пополнения нажать «обновить» и ввести 130 000, P&L стал бы +30 000. Намерение
различает кнопка, не число (C-7′, C-26).

### П-3б. Обновление и пополнение в один день

Вчера карта = 80 000. Сегодня обновление до 85 000, затем пополнение: ввод 95 000.

```
amount = 95 000;  capital_in = 10 000
PnL = 95 000 − 80 000 − 10 000 = 5 000 ₽              ✓ прибыль только от обновления
```

### П-3в. Трата без удаления

Вчера карта = 80 000. Сегодня расход: ввод 70 000.

```
amount = 70 000;  capital_out = 10 000
PnL = 70 000 − 80 000 − (−10 000) = 0 ₽               ✓ T-12
```

Если вместо расхода нажать «обновить» и ввести 70 000, P&L = −10 000.

### П-4. Архивирование: вывод денег

Вчера `Сбер1 = 10 000`, `Сбер2 = 20 000`. Сегодня `Сбер2` архивирована, `reason = WITHDRAWN`.

```
Cap(today) = 10 000;  Withdrawal = 20 000;  NetFlow = −20 000
PnL = 10 000 − 30 000 − (−20 000) = 0 ₽      ✓
```

### П-5. Архивирование: перевод на другую карту

Остаток `20 000` переносится на `Сбер1` в той же транзакции: `Сбер1 = 30 000`, потока нет.

```
PnL = 30 000 − 30 000 − 0 = 0 ₽              ✓
```

Без механизма C-3 этот сценарий давал бы `+20 000 ₽` фантомной прибыли.

### П-5б. Архивирование: деньги потеряны

Те же входные данные, что в П-4 и П-5, но `reason = LOST`. Поток не создаётся.

```
Cap(today) = 10 000;  Withdrawal = 0;  NetFlow = 0
PnL = 10 000 − 30 000 − 0 = −20 000 ₽        ✓ убыток равен остатку
```

Три примера П-4, П-5 и П-5б — одни и те же числа и три разных ответа: `0`, `0` и `−20 000`.
Разницу задаёт исключительно выбор пользователя в диалоге, вычислить её из данных нельзя.
Именно поэтому вопрос обязателен при непустом остатке (C-17).

### П-6. Пропущенные дни

Обновления: 10 августа → 100 000, 14 августа → 103 000. 11–13 августа записей нет.

```
prev(14 авг) = 10 авг;  periodDays = 4
DailyPnL = 103 000 − 100 000 = 3 000 ₽;  Return = 3.00%
```
UI: `+3 000 ₽ (+3.00%) · за 4 дня`. Синтетические нули не создаются (§9).

### П-7. Первая карта

Создана первая карта на `10 000`. `TotalDeposits = 10 000`.

```
TotalPnL    = 10 000 − 10 000 + 0 = 0 ₽
TotalReturn = 0 / 10 000 = 0.00%
```

Стартовый баланс не прибыль (C-29). Если эти 10 000 уже содержат заработок, путь такой:
создать с внесённым (или с нулём), затем обновить до факта.

### П-7б. Заморозка не меняет прибыль

Вчера две карты: 80 000 в работе и 20 000. Сегодня вторую заморозили.

```
Cap = 100 000;  WorkCap = 80 000;  FrozenCap = 20 000
PnL = 100 000 − 100 000 − 0 = 0 ₽                    ✓ T-11
```

### П-8. Исправление опечатки в день создания

Создана карта `30 000`, тут же исправлена на `3 000`.
`capital_in` вытесняется вместе с суммой ⟹ `Deposit = 3 000`, `Cap = 3 000`, `PnL = 0 ₽`.
См. §4.

## 8. Денежная арифметика и округление

| Правило | Значение |
|---|---|
| Тип хранения | `NUMERIC(20,2)`: ёмкость типа до `999 999 999 999 999 999.99` |
| Предел ввода и записи | `±1 000 000 000 000 000.00` (`±10^15`) — C-10, `CHECK` в `balance_entries` |
| Тип в коде | `Money` — branded-тип над `Decimal`, шкала строго 2 |
| Точность вычислений | `Decimal` с precision 34 (decimal128-класс) |
| Округление денег | `ROUND_HALF_UP` до 2 знаков, только на границе вывода/записи |
| Округление процентов | `ROUND_HALF_UP` до 2 знаков, только при отображении |
| Промежуточные значения | Не округляются. Округление — последняя операция. `Money` может держать сумму капитала выше `10^15` — это промежуточный итог, в строку баланса он не пишется |
| Ввод | > 2 знаков после запятой отклоняется с ошибкой, без молчаливого округления (C-12). Значение вне `±10^15` отклоняется сообщением «Слишком большое значение», а не падением |
| Деление | Только при расчёте процентов. Деньги никогда не делятся на деньги с записью результата |

**Запрещено:** `number` для денег · `parseFloat` · `Number()` над `Decimal` · `Math.round`
· `toFixed` для расчётов · JSON-числа для денег (в `JSONB` и FSM-состоянии деньги — строки)
· `SUM()` по деньгам в SQL (NFR-11) · неявное `Decimal → number`.

Форматирование: `116 000 ₽` (узкий пробел U+202F как разделитель разрядов), копейки
опускаются при `.00`, знак всегда явный для дельт (`+1 200 ₽`, `−450 ₽`), для процентов
`+1.05%`. Отсутствующее значение — `—` (em dash).
