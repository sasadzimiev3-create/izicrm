# izicrm — план реализации по этапам

Документ существует ради одной цели: чтобы задачу агенту можно было поставить одной фразой
«выполни этап N из `docs/roadmap.md`» и получить предсказуемый результат.

Каждый этап устроен так, что его можно проверить, **не приступая к следующему**. Если этап
нельзя принять отдельно, он разбит неправильно.

---

## 0. Как ставить задачу агенту

### Один этап — один чат

Новый чат на каждый этап. Причина не в удобстве: контекст агента конечен, и к концу большой
задачи первые сообщения вытесняются. Агент, дописывающий Excel-отчёт в том же чате, где
двести сообщений назад обсуждались форматы денег, вспомнит правила округления хуже, чем
свежий агент, прочитавший `financial-model.md` §8.

### Шаблон задачи

```
Выполни этап N из docs/roadmap.md.

Перед началом прочитай AGENTS.md и документы, указанные в этапе.
Не выходи за границы этапа: файлы других этапов не трогай.
Когда закончишь — прогони проверки из раздела «Готово, когда» и покажи результат.
```

Больше ничего писать не нужно. Всё остальное агент найдёт в документации — она для этого
и написана.

### Чего в задаче быть не должно

| Формулировка | Что с ней не так |
|---|---|
| «Сделай бота» | Нет границы. Агент выберет её сам, и почти наверняка не ту |
| «Реализуй первый этап» без этого файла | «Первый» — по чьей нумерации? |
| «Сделай как лучше» | В проекте 21 разобранное противоречие. «Как лучше» уже решено, это надо прочитать, а не изобретать |
| «Заодно поправь Х» | Задача перестала быть проверяемой: непонятно, что принимать |

### Признак правильно поставленной задачи

Вы можете принять работу, **не читая код** — по прохождению проверок из «Готово, когда».
Если для приёмки нужно вчитываться в реализацию, этап слишком большой или критерии размыты.

## 1. Порядок и зависимости

```
Этап 0  каркас
   │
   ├── Этап 1  деньги ──── Этап 2  финансовое ядро ──┐
   │                                                 │
   └── Этап 3  база данных ─── Этап 4  репозитории ──┤
                                                     │
                                          Этап 5  сценарии
                                                     │
                                        ┌────────────┴────────────┐
                                   Этап 6  Telegram        Этап 7  Excel
                                        └────────────┬────────────┘
                                                     │
                                            Этап 8  развёртывание
```

Ветви `1 → 2` и `3` независимы: они не делят ни одного файла, их можно вести параллельно
в двух чатах. Всё остальное — строго последовательно, потому что каждый следующий этап
вызывает код предыдущего.

Параллелить этапы, редактирующие одни и те же файлы, нельзя: два агента перезапишут работу
друг друга, и git это не спасёт — конфликта не возникнет, просто победит тот, кто сохранил позже.

## Этап 0. Каркас проекта

**Цель.** Пустой, но работающий проект: команды из `AGENTS.md` запускаются и проходят.

**Читать:** `AGENTS.md`, `docs/architecture.md` §2–3.

**Создать:**

- `package.json` — Node 24, ESM, зависимости из `architecture.md` §2 с точными версиями
- `tsconfig.json` — `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`
- `eslint.config.js` — включая правило границ слоёв из `architecture.md` §2.2
- `vitest.config.ts` — порог покрытия `src/domain/finance/**` = 100% строк и ветвей
- пустая структура каталогов `src/` по `architecture.md` §3
- `.env.example`
- `README.md` — запуск за пять команд

**Готово, когда:**

```bash
npm run typecheck   # проходит
npm run lint        # проходит
npm test            # проходит (тестов пока нет — это нормально)
```

и `npm run lint` **падает** на искусственном импорте `grammy` внутри `src/domain/` —
правило границ должно работать, а не просто присутствовать в конфиге.

Последняя проверка обязательна. Правило, которое никто не проверил, обычно не работает,
и обнаруживается это через два месяца, когда SQL уже просочился в домен.

## Этап 1. Деньги

**Цель.** Тип денег и всё, что с ним делают. Ни одной строки бизнес-логики.

**Читать:** `AGENTS.md`, `docs/financial-model.md` §8, `.cursor/rules/financial-math.mdc`.

**Создать:** `src/domain/money/` — `money.ts`, `parse.ts`, `format.ts`, `percent.ts`
плюс тесты в `tests/unit/money/` и `tests/property/money/`.

**Готово, когда:**

- `Money` не позволяет создать себя из `number` — это ошибка типизации, а не проверка в рантайме
- `parseAmount` принимает `10000`, `10 000`, `10.000,50`, `1 234,56 ₽` и отвергает мусор
- `formatMoney` даёт `1 000 327 ₽` с узким пробелом U+202F, копейки при `.00` опущены (C-21)
- `PercentResult` невозможно отобразить как `0%`, когда значение не определено (C-2)
- property-тест: `parse(format(x)) = x` для любого `x`
- покрытие 100% строк и ветвей

**Почему этап первый.** От него зависит всё остальное, а сам он не зависит ни от чего —
ни от базы, ни от Telegram. Ошибка здесь тиражируется в каждую формулу, поэтому этап
маленький и покрыт плотнее прочих.

## Этап 2. Финансовое ядро

**Цель.** Все формулы прибыли. Чистые функции: без I/O, без SQL, без `Date.now()`.

**Читать:** `docs/financial-model.md` целиком, `docs/requirements.md` §4 (реестр C-1…C-21).

**Создать:** `src/domain/finance/` — `balance.ts`, `card-scope.ts`, `capital.ts`, `flows.ts`,
`pnl.ts`, `dietz.ts`, `card-change.ts`, `period.ts`; тесты в `tests/unit/finance/`
и `tests/property/finance/`.

**Готово, когда:**

- реализованы все 26 сценариев матрицы `financial-model.md` §10, включая FT-08d…FT-08f
- теоремы T-1…T-9 оформлены как property-тесты, а не как примеры с фиксированными числами
- воспроизводятся все примеры П-1…П-8, П-5б с точностью до копейки
- `periodPnl` — единственное место, где считается прибыль; `dailyPnl`, `monthlyPnl`,
  `allTimePnl` вызывают её и ничего не вычисляют сами
- текущая дата приходит параметром, `Date.now()` в каталоге отсутствует
- покрытие 100% строк и ветвей — CI-гейт

**Главный риск.** Соблазн посчитать прибыль как сумму изменений по картам. Это даёт верный
ответ на простых данных и неверный — при переводе между своими картами. T-1 ловит именно это,
поэтому тест пишется до реализации.

## Этап 3. База данных

**Цель.** Схема, миграции, RLS. Кода приложения этап не касается — можно вести параллельно
с этапами 1 и 2.

**Читать:** `docs/database.md` целиком, `.cursor/rules/security.mdc`,
`.cursor/rules/database.mdc`.

**Создать:** `migrations/NNN_*.sql`, `src/infrastructure/db/pool.ts`, `user-context.ts`,
тесты в `tests/integration/db/` и `tests/security/`.

**Готово, когда:**

- `npm run migrate:up` и откат проходят на чистой базе
- запрос **без** контекста пользователя возвращает ноль строк
- запрос **с чужим** контекстом возвращает ноль строк
- `INSERT` с чужим `user_id` падает на `WITH CHECK`
- `UPDATE` суммы и `DELETE` финансовой записи блокируются триггером
- роль приложения не имеет `SUPERUSER`, `BYPASSRLS` и права `DELETE` — проверено запросом
  к системным таблицам, а не глазами
- `v_capital_flows` не возвращает строк для карт с `TRANSFERRED` и `LOST`

**Осторожно с `LOST`.** Условие во вью написано как `archive_reason = 'WITHDRAWN'`, а не
`<> 'TRANSFERRED'`. Если «упростить» его до отрицания, все убытки от потерянных карт молча
превратятся в выводы и исчезнут из расчёта. Тест на это обязателен.

## Этап 4. Репозитории и Unit of Work

**Цель.** Доступ к данным. Бизнес-логики нет.

**Читать:** `docs/architecture.md` ADR-002, ADR-008; `docs/database.md` §6;
`.cursor/rules/security.mdc`.

**Зависит от:** этапы 1, 2, 3.

**Создать:** `src/application/ports/*`, `src/infrastructure/repositories/*`,
`src/infrastructure/db/unit-of-work.ts`.

**Готово, когда:**

- у каждого метода репозитория `userId` — **первый обязательный параметр**; метода без него
  не существует физически
- `withUser` выставляет контекст через `set_config(..., true)`, то есть `LOCAL`
- деньги читаются как строки и превращаются в `Money`; `SUM()` по деньгам в SQL отсутствует
- тест на пул соединений: после транзакции пользователя A соединение возвращается в пул
  и запрос пользователя B не видит данных A

**Последний пункт — не формальность.** Забытый третий аргумент в `set_config` не ломает
ничего до тех пор, пока пользователь один. Проблема проявится в проде, у второго пользователя,
и будет выглядеть как мистика.

## Этап 5. Сценарии приложения

**Цель.** Пользовательские операции целиком: дашборд, создание карты, обновление балансов,
удаление материала.

**Читать:** `docs/architecture.md` §4, `docs/requirements.md` FR-1…FR-5,
`docs/financial-model.md` §4.2 (три причины архивирования).

**Зависит от:** этапы 2, 4.

**Создать:** `src/application/services/*`, `src/application/dto/*`.

**Готово, когда:**

- удаление материала с остатком реализовано во всех трёх ветвях; интеграционный тест
  проверяет инвариант `PnL(TRANSFERRED) = PnL(WITHDRAWN) = PnL(LOST) + X` на одних данных
- перевод остатка на другую карту происходит в одной транзакции с архивированием
- сервисы не знают о Telegram: ни `grammy`, ни `ctx`, ни текстов сообщений
- повторный вызов операции с тем же ключом идемпотентности не создаёт вторую запись

## Этап 6. Telegram: FSM и экраны

**Цель.** Интерфейс. Арифметики и SQL нет.

**Читать:** `docs/telegram-flows.md` целиком, `.cursor/rules/telegram-ui.mdc`.

**Зависит от:** этап 5.

**Создать:** `src/interface/telegram/**`, `src/infrastructure/telegram/bot.ts`, `src/main.ts`.

**Готово, когда:**

- функция перехода чистая и тестируется без Telegram
- каждый переход, касающийся карты, перепроверяет владение через `getUserCard(userId, cardId)`;
  тест с чужим `card_id` в `callback_data` даёт ноль изменений в базе
- чужой и несуществующий `card_id` дают **одинаковый** ответ «Карта не найдена»
- главный экран сходится: сумма материалов равна общему балансу (T-6)
- в текстах интерфейса слово «карта» не встречается — только «материал» (C-18)
- устаревший `callback_data` со старым `state_rev` не выполняет действие повторно

**Цель.** Восемь листов с графиками.

**Читать:** `docs/excel-report.md` целиком.

**Зависит от:** этапы 2, 4. С этапом 6 не пересекается — можно параллельно.

**Создать:** `src/infrastructure/excel/**`, `src/application/services/report.service.ts`.

**Готово, когда:** проходят XL-01…XL-13, включая XL-07 (в отчёте пользователя A нет ни одного

Больше нигде это не разрешено.

## Этап 8. Развёртывание

**Цель.** Бот работает на сервере и переживает перезагрузку.

**Зависит от:** этап 6.

**Готово, когда:** systemd поднимает бота после `reboot`; миграции применены; настроен
ежедневный бэкап базы с проверенным **восстановлением**.

Бэкап, из которого ни разу не восстанавливались, бэкапом не является. Проверка входит в этап.

## 2. Что делать, если этап оказался велик

Признак: агент к концу работы забывает договорённости из начала, или проверок в «Готово, когда»
больше восьми. Тогда этап делится по файлам, а не по «сделай половину»: например, этап 2
разбивается на «балансы, scope, капитал» и «потоки, P&L, Dietz». Граница проходит там, где
проходит граница между файлами, — иначе следующий агент получит полуготовый модуль
и не поймёт, что в нём уже работает.
