# izicrm — Требования

Персональный Telegram-бот — калькулятор оборота по банковским картам (в интерфейсе —
«материалы»). Пользователь видит, сколько денег есть сейчас, сколько в работе, сколько
заморожено и сколько заработано за период. Валюта: **только RUB**. Мультивалютность вне scope.

Прибыль появляется **только из разницы при обновлении балансов**. Создание материала
и пополнение существующего — не прибыль: это внешний ввод денег в учёт.

Документ — нормализованный источник требований. Каждое требование имеет ID и трассируется
в тесты (`docs/financial-model.md` §10) и код.

Статус: **этап 0 выполнен**; требования обновлены 24.08.2026 (C-26…C-29).
Реализация финансового ядра ещё не начата.

## 1. Глоссарий

| Термин | Определение |
|---|---|
| **Карта** (Card) | Именованный счёт пользователя. Не хранит номер карты, только название. В интерфейсе — «материал» (C-18). |
| **Баланс** (Balance) | Значение денег на карте на конкретную **бизнес-дату**. |
| **Бизнес-дата** | Календарная дата в таймзоне пользователя (`Europe/Moscow` по умолчанию). Не UTC-дата. |
| **Запись баланса** (Balance entry) | Неизменяемый факт: (карта, бизнес-дата, сумма, вход капитала, источник). |
| **Актуальная запись** | Единственная не-вытесненная (`superseded_at IS NULL`) запись на (карта, дата). |
| **LOCF** | Last Observation Carried Forward — баланс на дату D = последняя актуальная запись с `effective_date ≤ D`. |
| **Капитал** (Capital) | Сумма LOCF-балансов всех карт в scope на дату D. Общий баланс на главном экране. |
| **В работе** (Working capital) | Капитал карт в scope, которые **не** заморожены. Деньги, доступные в работе. В интерфейсе — «В работе». |
| **Заморожено** (Frozen capital) | Капитал карт в scope со статусом «заморожена». Деньги на месте, но временно не в работе. |
| **In scope на D** | `created_on ≤ D AND (archived_on IS NULL OR D < archived_on)`. Заморозка scope не меняет. |
| **Внешний поток** (Capital flow) | Ввод/вывод денег из системы учёта. Не является P&L. |
| **Депозит** (Deposit) | Внешний ввод: начальный баланс новой карты **или** пополнение существующей. |
| **Пополнение** (Top-up) | Операция: пользователь вводит **новый баланс** материала, больший текущего. Разница `Δ` — депозит. P&L не меняется. |
| **Расход (трата)** (Spend) | Операция: пользователь вводит **новый баланс** материала, меньший текущего, без удаления карты. Разница — вывод. P&L не меняется. |
| **Вывод** (Withdrawal) | Внешний вывод: трата с карты (FR-9) **или** остаток карты, архивированной с причиной `WITHDRAWN`. |
| **P&L** | Изменение капитала, очищенное от внешних потоков. Единственная мера прибыли. Возникает только из обновления балансов. |
| **Изменение баланса карты** | Дельта по одной карте. **Информационная метрика, не прибыль** (см. FR-5.4). |

### C-1. §5 даёт ложную прибыль при добавлении карты — прямое противоречие с §6

**Проблема.** §5 определяет `DailyProfit = TotalToday − TotalPrevious`, где `TotalPrevious` —
сумма предыдущих балансов активных карт. Карта, созданная сегодня, предыдущего баланса не имеет.
При трактовке «нет записи → 0» добавление карты на 30 000 ₽ даёт `DailyProfit = +30 000 ₽`.

§6 требует прямо противоположного: начальный баланс новой карты не является доходом.

**Почему это ошибка.** Формула §5 не содержит члена для внешних потоков, но §6 требует его наличия.
Формулы §5 и §6 несовместимы.

**Решение.** Дневная формула получает тот же член внешних потоков, что и месячная:

```
DailyPnL(D) = Capital(D) − Capital(prev) − NetFlow(prev, D]
```

Дневной и месячный P&L становятся частными случаями одной функции `periodPnl(from, to)` (FR-5.9).

---

### C-2. Деление на ноль в формуле процента

**Проблема.** `DailyProfitPercent = DailyProfit / TotalPrevious * 100`. Требования не описывают
`TotalPrevious = 0`. Реально достижимо: все карты в нуле; все карты архивированы.

**Почему это ошибка.** Деление на ноль. При `TotalPrevious = 0` и `DailyProfit > 0` доходность
математически не определена (бесконечна), а не равна нулю.

**Решение.** Процент определён только при `base > 0`. Иначе выводится `—`. Реализуется как
`PercentResult = { defined: true, value: Decimal } | { defined: false, reason: 'ZERO_BASE' | 'NO_PREVIOUS' }`.
Тип запрещает «случайно» получить число. Отрицательная база (кредитная карта в минусе) также даёт `—`.

### C-3. Архивирование карты создаёт фантомный P&L — требования не покрывают этот случай **[РЕШЕНО: расширение принято]**

**Проблема.** §4 говорит, что архивная карта не участвует в текущем капитале, но не говорит, что
происходит с P&L в день архивирования. Капитал падает на остаток карты.

Разбор случаев (вчера: Сбер1 = 10 000, Сбер2 = 20 000, капитал = 30 000):

| Сценарий | Без обработки потока | Корректно |
|---|---|---|
| Архив Сбер2, деньги сняты в банкомате | P&L = −20 000 (ложный убыток) | P&L = 0 |
| Перевод 20 000 на Сбер1 (Сбер1 = 30 000), затем архив Сбер2 без обнуления | P&L = +20 000 (ложная прибыль) | P&L = 0 |

**Почему это ошибка.** Нарушается FR-5.3 («количество карт не влияет на P&L») и §7
(«P&L отражает реальное изменение капитала, а не изменение количества карт»).
Отличить вывод от внутреннего перевода по данным невозможно — информации физически нет.

**Решение.** Архивирование карты с ненулевым остатком требует одного уточняющего вопроса:

- `[💸 Деньги выведены]` → `WITHDRAWAL` на сумму остатка. Капитал ↓, P&L = 0.
- `[↔️ Переведены на другую карту]` → выбор карты-получателя; в одной транзакции остаток
  прибавляется к балансу получателя за ту же бизнес-дату, поток не создаётся. Капитал не меняется, P&L = 0.

При нулевом остатке вопрос не задаётся.

**Обоснование расширения.** Это минимальный механизм, без которого заявленный в §1 и §7 инвариант
недостижим ни при каком порядке действий пользователя. Логика выведена из требований, не придумана.

**Статус: подтверждено заказчиком 20.08.2026, расширено 23.08.2026 (C-17).** Механизм принят.
К двум вариантам выше добавлен третий — `[📉 Потерял]` (`LOST`): капитал падает на остаток,
поток не создаётся, и падение становится убытком. Он не отменяет анализ этого пункта: ложных
`±20 000` из таблицы выше по-прежнему не возникает, но появился случай, когда убыток настоящий
и должен быть показан. Актуальные формулировки кнопок — C-17.

**Теорема (следствие).** Внешний поток нужен ровно тогда, когда карта входит в активное множество
или выходит из него. Пока обе карты активны, перевод между ними автоматически даёт P&L = 0, потому
что капитал не изменился — специальная операция «перевод» между активными картами не нужна.

### C-4. «Относительно начала месяца» — двусмысленно и в одной трактовке теряет прибыль за 1-е число

**Проблема.** §7: «месячная статистика считается относительно начала месяца». Два чтения:
`Capital(1-е число)` или `Capital(последний день предыдущего месяца)`.

**Почему это ошибка.** Если взять `Capital(1 августа)`, а пользователь обновил балансы 1 августа,
то прибыль за 1 августа попадает в базу отсчёта и **исчезает** из августовского P&L. Месячные P&L
перестают складываться в общий P&L.

**Решение.** Базой служит закрытие предыдущего дня: `OpeningCapital(M) = Capital(S − 1 день)`.
Это делает периоды непересекающимися и сохраняет аддитивность (`docs/financial-model.md` §6).

### C-5. Макет §10 внутренне противоречив по округлению процентов

**Проблема.** Проверка чисел макета:

| Строка макета | Восстановленная база | Точный процент | HALF_UP | Обрезание |
|---|---|---|---|---|
| `СЕГОДНЯ +1 200 ₽ (+1.04%)` | 114 800 | 1.045296…% | **1.05%** | **1.04%** |
| `Сбер2 +700 ₽ (+3.4%)` | 20 600 | 3.398058…% | **3.4%** | **3.3%** |

Значение «сегодня» требует обрезания, значение «Сбер2» требует округления. Одновременно оба
недостижимы. Дополнительно: `10 500 + 21 300 + 7 800 = 39 600 ≠ 116 000` — список карт не сходится
с показанным капиталом; разное число знаков (`5.0%` против `1.04%`).

**Решение.** Единое правило: проценты округляются `ROUND_HALF_UP` до **2 знаков**, деньги — до
копеек, `.00` при отображении опускается. По этому правилу корректное значение в макете — `+1.05%`.
Инвариант «Σ балансов активных карт = показанный капитал» закрепляется тестом.

**Набор метрик доходности (подтверждено 20.08.2026).** В Telegram выводится только простая
доходность `PnL / OpeningCapital`, как в требованиях. В Excel к ней добавляются Modified Dietz
и time-weighted return — они расходятся с простой ровно тогда, когда в периоде были внешние
потоки, и это расхождение само является полезной информацией.

### C-6. §3 и §11 задают разную область уникальности названия

**Проблема.** §3: «уникальным в пределах одного пользователя». §11: «не допускать две **активные**
карты с одинаковым названием».

**Решение (подтверждено).** Принимается более узкая формулировка §11: частичный unique-индекс
`(user_id, name_norm) WHERE archived_on IS NULL`. Название архивированной карты можно переиспользовать.
Дополнительно нормализация: `trim`, сжатие внутренних пробелов, регистронезависимое сравнение —
чтобы `«Сбер1»`, `«сбер1»` и `«Сбер1 »` не были разными картами. Отчёты различают одноимённые карты по ID.

### C-7. §2 закрывает модель: реальное пополнение будет учтено как прибыль **[ПЕРЕОТКРЫТО И ЗАКРЫТО 24.08.2026]**

**Проблема (исходная).** §2 запрещала спрашивать, является ли изменение прибылью или
пополнением. Единственные внешние потоки — создание и архивирование карты. Приход денег
на уже существующую карту учитывался как прибыль.

**Прежнее решение (20.08.2026, отменено).** Считать это осознанным ограничением v1
(аксиома A-3), без отдельных операций пополнения/снятия. Оговорка выводилась в лист
«Инфо» Excel-отчёта.

**Почему переоткрыто.** Заказчик 24.08.2026 явно описал продукт иначе: пополнение —
отдельное действие («пополнить баланс уже имеющегося материала»), и эта сумма **не**
является чистым плюсом. Прибыль — только разница при обновлении балансов
(80 000 → 90 000 = +10 000). Прежнее A-3 этому противоречит.

**Новое решение.** Операция пополнения входит в v1 (FR-8, C-26). Аксиома A-3 расширена:
внешний поток возникает не только на границах жизни карты, но и при пополнении.
Ограничение «зарплата на карте = прибыль» снимается: для ввода денег есть кнопка
«Пополнить», для заработка — «Обновить балансы».

Если пользователь обновит баланс, не отметив пополнение, прирост по-прежнему станет
прибылью. Это уже не дыра модели, а цена выбранного действия: две кнопки различают
намерение, система его не угадывает.

### C-8. Не определена таймзона и граница суток **[принято по умолчанию, меняется конфигурацией]**

**Проблема.** «Раз в день» — по какому времени? При UTC обновление в 01:00 МСК попадёт в предыдущую дату.

**Решение.** Бизнес-дата вычисляется в таймзоне пользователя; по умолчанию `Europe/Moscow`
(нет переходов на летнее время, соответствует RUB). Поле `users.tz` заложено в схему.
Дополнительно хранится `recorded_at TIMESTAMPTZ` для аудита. Все даты в БД — `DATE` (бизнес-дата),
все моменты времени — `TIMESTAMPTZ`.

### C-9. Не определены разархивирование и история переименований

**Решение (v1).**
- Разархивирование не поддерживается: обратная операция потребовала бы депозита на восстановленный
  остаток и усложнила бы модель потоков. Пользователь создаёт новую карту.
- Переименование не версионируется: отчёты показывают текущее название. Идентичность карты — `card_id`,

### C-10. Не определён формат ввода суммы

**Решение.** Принимаются: цифры, пробелы/узкие пробелы/подчёркивания как разделители разрядов,
`,` или `.` как десятичный разделитель, не более 2 знаков после разделителя, опциональный ведущий `−`.
Отклоняются: выражения, `1e5`, `10k`, третий знак после запятой (**с ошибкой, без молчаливого
округления** — см. C-12), значения вне `±10^15`. Относительный ввод (`+500`) не поддерживается:
он противоречит семантике «введите текущий баланс».

### C-11. Диалог, начатый до полуночи, может «размазаться» по двум датам

Часть карт попадёт в август, часть в сентябрь — оба месячных P&L будут искажены.

**Решение.** Бизнес-дата вычисляется один раз при старте диалога, хранится в состоянии FSM

### C-12. `NUMERIC(20,2)` неявно округляет — это нарушает NFR-4

**Проблема.** PostgreSQL при вставке `10000.005` в `NUMERIC(20,2)` молча округлит до `10000.01`.
Это ровно то неявное округление, которое запрещено §15.

**Решение.** Валидация на входе отклоняет более 2 знаков после запятой с понятным сообщением.
БД остаётся вторым барьером. Драйвер `pg` возвращает `NUMERIC` как строку — запрещено регистрировать
type parser, превращающий его в `number`; на это есть отдельный тест.

### C-13. «Удалить» карту противоречит запрету физического удаления

**Проблема.** §1 говорит «удалять/архивировать», §4 запрещает физическое удаление финансовых данных.

**Решение.** Операция удаления отсутствует. В UI кнопка называется «Архивировать» с пояснением
«история сохранится». `ON DELETE RESTRICT` на всех финансовых FK как технический барьер.

### C-14. Блок «сегодня» вводит в заблуждение, если сегодня обновлений не было

**Проблема.** При LOCF `Capital(сегодня) = Capital(последнего обновления)`, поэтому блок «СЕГОДНЯ»
покажет `+0 ₽ (0.00%)`, хотя пользователь просто не обновлял балансы. §9 при этом запрещает
предупреждать о пропущенных днях.

**Решение.** Блок озаглавливается фактической датой последнего обновления: `СЕГОДНЯ · 20 августа`,
если обновление было сегодня, иначе `ПОСЛЕДНЕЕ ОБНОВЛЕНИЕ · 16 августа`. При интервале более
одного дня добавляется `за N дней`. Предупреждений нет — только честная подпись. Бизнес-логика не меняется.

### C-15. Не определена база доходности за всё время

**Проблема.** Простая доходность `P&L / OpeningCapital` для периода «за всё время» имеет базу 0
(до первой карты капитала не было) — не определена.

**Решение.** За всё время база — сумма депозитов (реально внесённые деньги):
`TotalReturn = TotalPnL / TotalDeposits`. Если депозитов нет (все старты и пополнения
нулевые) — `—`. Дополнительно в Excel выводится Modified Dietz как взвешенная по времени
альтернатива.

### C-16. Проценты не складываются — это нужно явно зафиксировать

**Проблема.** Рублёвые P&L аддитивны (телескопирование), проценты — нет: сумма дневных процентов
≠ месячный процент.

**Решение.** Аддитивность рублей закрепляется property-тестом. Проценты никогда не суммируются.
В Excel рядом с простой доходностью выводится time-weighted return `Π(1 + rᵢ) − 1` как корректная
composed-метрика.

### C-17. Кнопка «Удалить материал» и судьба остатка **[РЕШЕНО 23.08.2026]**

**Решение.** Кнопка называется «Удалить материал», действие — архивирование: история сохраняется,
физического удаления нет. При ненулевом остатке задаётся вопрос с **тремя** вариантами, каждый
из которых называет последствие для прибыли в тексте кнопки:

| Вариант | `archive_reason` | Капитал | Поток | Прибыль |
|---|---|---|---|---|
| Перевёл на другую карту | `TRANSFERRED` | не меняется | нет | не меняется |
| Вывел (снял, потратил) | `WITHDRAWN` | падает на `X` | `−X` | не меняется |
| Потерял | `LOST` | падает на `X` | нет | **убыток `X`** |

Значение `LOST` добавлено в `archive_reason` — это новый исход, которого в C-3 не было.
Формулировки «записать сумму как плюс / как минус» отклонены: они допускали три несовместимых
прочтения (разбор в C-17.1 ниже сохранён как обоснование).

Затронутые документы: `financial-model.md` §4.2 (третья ветвь `deriveWithdrawal`), теорема T-9
и пример П-5б, `database.md` §3.3 и §4.2, `telegram-flows.md` §4. Теоремы T-3 и T-4 остаются
в силе: `LOST` под T-3 сознательно не попадает, для него доказана отдельная граница T-9.

Ниже — исходный разбор, сохранён для истории.

### C-17 (исходная формулировка). Кнопка «Удалить материал» против запрета удаления данных

**Проблема.** Вёрстка от 23.08.2026 содержит кнопку `[🗑 Удалить материал]`. При этом §4 исходных
требований запрещает физическое удаление финансовых данных, а C-13 уже закрыл этот вопрос в пользу
архивирования: истории удалять нельзя, иначе рушится вся модель P&L за прошлые периоды.

**Почему это ошибка.** Настоящее удаление материала уничтожило бы его балансы, а вместе с ними —
корректность P&L за все месяцы, когда материал существовал. Отчёты за прошлое стали бы врать
задним числом. Плюс это нарушает аксиому A-4 (append-only) и триггеры в БД.

**Варианты.**

1. **Кнопка называется «Удалить», действие — архивирование.** Пользователь видит привычное слово,
   данные сохраняются. В подтверждении честно написано: «История сохранится и останется в отчётах».
   Технически это ровно операция архивирования из C-3, включая вопрос о судьбе остатка.
2. Переименовать кнопку в «Архивировать» — точнее по смыслу, но менее привычно.
3. Настоящее удаление — **отклоняется**: несовместимо с §4 и с расчётом P&L за прошлые периоды.

**Рекомендация:** вариант 1. Слово из вёрстки сохраняется, поведение остаётся корректным.

#### C-17.1. Уточнение от 23.08.2026: «записать сумму как плюс / как минус»

**Что сказано.** После нажатия «удалить материал» пользователю задаётся вопрос с двумя вариантами:
«записать сумму как плюс?» и «записать сумму как минус». Это заменяет формулировки из C-3
(«деньги выведены» / «переведены на другую карту»).

**Почему нельзя реализовать как есть.** Слова «плюс» и «минус» не определяют, к какой величине
относится знак. Возможных прочтений три, и они дают **разную прибыль на одних и тех же данных**.
Разбор на числах вёрстки: капитал 1 000 327 ₽ (Сбер 124 276, Альфа 318 861, ВТБ 557 190),
удаляется Альфа с остатком 318 861 ₽.

Основная формула: `PnL = Cap(B) − Cap(A−1) − NetFlow`.

| Прочтение | Вариант | Капитал после | Записанный поток | P&L за день |
|---|---|---|---|---|
| 1. Знак движения капитала | «минус» — деньги выведены наружу | 681 466 | −318 861 | **0** |
| 1. Знак движения капитала | «плюс» — деньги переведены на ВТБ (→ 876 051) | 1 000 327 | 0 | **0** |
| 2. Знак вклада в прибыль | «плюс» — сумма считается заработком | 681 466 | −637 722 | **+318 861** |
| 2. Знак вклада в прибыль | «минус» — сумма считается убытком | 681 466 | 0 | **−318 861** |
| 3. Смешанное | «плюс» — деньги не потеряны | 681 466 | −318 861 | **0** |
| 3. Смешанное | «минус» — деньги потеряны | 681 466 | 0 | **−318 861** |

Разброс по одному и тому же действию — от −318 861 до +318 861 ₽. Пока прочтение не выбрано,
кнопку реализовать нельзя.

**Оценка прочтений.**

Прочтение 1 совпадает с уже принятым C-3 и сохраняет теоремы T-3 и T-4: перемещение денег между
своими картами и вывод наружу прибыли не создают. Требует доработки: вариант «как плюс» не говорит,
**на какую карту** зачислена сумма, без этого капитал не сходится.

Прочтение 3 тоже согласовано с моделью и добавляет то, чего в C-3 не было: возможность объявить
остаток потерянным. Это осмысленный случай (деньги действительно потрачены или списаны), но слово
«плюс» для нейтрального исхода вводит в заблуждение.

Прочтение 2 в ветке «плюс» **не имеет физического смысла**: чтобы капитал упал на 318 861 и прибыль
при этом выросла на 318 861, в журнал придётся записать вывод 637 722 ₽ — сумму, которой не было.
Ветка нарушает A-3 (каждый поток соответствует реальному перемещению денег) и ломает T-3.

**Не покрытый случай.** Оба предложенных варианта молчат о нулевом остатке. При остатке 0 вопрос
задавать не нужно: ни один знак ничего не меняет, лишний экран только провоцирует ошибку.

**Выбрано заказчиком 23.08.2026:** прочтение 1 с явными формулировками вместо «плюс/минус»,
дополненное третьим вариантом из прочтения 3:

```
Остаток на «Альфа 7131*» — 318 861 ₽. Что с ним?
1) Перевёл на другую карту → выбрать карту, сумма зачислится туда, прибыль не изменится
2) Вывел из учёта (снял, потратил) → капитал уменьшится, прибыль не изменится
3) Потерял → капитал уменьшится, это будет убыток 318 861 ₽
```

Формулировки называют последствие для прибыли прямо в кнопке, поэтому ошибиться сложнее,
чем при выборе между «плюс» и «минус».

### C-18. Термин «материал» вместо «карта» **[РЕШЕНО 23.08.2026]**

**Решение.** «Материал» — то же, что карта, выбрано как более удобное слово в интерфейсе.
Расширения предметной области нет: учитываются банковские карты.

Принят вариант 1: **в интерфейсе «материал», в коде и БД остаётся `card`** (`cards`, `Card`,
`getUserCard`). Расхождение терминов сознательное и локализовано в слое `interface/telegram/views`,
где строятся тексты. Словарь соответствий фиксируется в `docs/telegram-flows.md`, чтобы
переименование интерфейса не требовало трогать домен и базу.

Ниже — исходный разбор вопроса, сохранён для истории.

---

**Проблема.** В присланной вёрстке сущность называется «материал», хотя исходные требования и вся
документация используют «карта» (`cards`, `Card`, `getUserCard`).

**Почему это важно.** Термин определяет имена таблиц, типов и методов во всём коде. Менять его
после начала реализации дорого. Кроме того, неясен смысл: «материал» может означать, что
учитываются не только банковские карты, а более широкий набор источников (наличные, вклады,
брокерские счета) — и тогда это не переименование, а расширение предметной области.

**Варианты.**

1. Только UI-термин: в интерфейсе «материал», в коде и БД остаётся `card`. Дёшево, но появляется
   расхождение между тем, что видит пользователь, и тем, что написано в коде.
2. Переименовать сущность целиком в нейтральное `Asset` / `assets` («актив»). Честно отражает
   расширенный смысл, момент идеальный — код ещё не написан.
3. Оставить «карта» везде, вёрстку поправить.

**Рекомендация:** вариант 2, если под «материалом» действительно понимается любой источник денег,
иначе вариант 3. **Нужен ответ: что именно вы учитываете — только банковские карты или что-то шире?**

### C-19. В новой вёрстке исчезла кнопка Excel-отчёта **[РЕШЕНО 23.08.2026]**

**Проблема.** Набор кнопок сократился до четырёх, `[📊 Excel-отчёт]` в нём нет. При этом §12
требований описывает отчёт подробно, и на него уже есть FR-7.1…FR-7.4 и спецификация
`docs/excel-report.md`.

**Решение.** Меню становится двухуровневым. На главном экране — четыре кнопки повседневных
действий из вёрстки. Под `[⚙️ Настройки]` уходят: Excel-отчёт (FR-7.1), переименование материала
(FR-2.10), смена стикера (C-20) и архив материалов (FR-2.6).

Из scope ничего не выпадает: FR-7.1…FR-7.4 и FR-2.6, FR-2.10 остаются в силе, меняется только
точка входа. Вариант «признать отчёт вне scope» отклонён — спецификация отчёта уже написана,
а он единственный способ увидеть историю глубже текущего месяца.

Архив материалов доступен только для чтения: разархивирование остаётся вне scope v1 (C-9).
Экран нужен по причине, не связанной с отчётностью: без него кнопка «Удалить материал» выглядела
бы обманом, поскольку данные на самом деле сохраняются.

### C-20. Смысл цветовых маркеров 🟢 🔴 🔵 **[РЕШЕНО 23.08.2026]**

**Проблема.** В вёрстке у материалов стоят цветные маркеры. Правило их выбора не задано, а по
образцу его восстановить нельзя: `Альфа` помечена красным при положительном изменении, то есть
со знаком P&L цвет не связан.

**Решение.** Маркеры — декоративные стикеры материала, которые выбирает пользователь.
Вычисляемой семантики нет: со знаком P&L, состоянием карты и любой метрикой цвет не связан.
Следствия:

- в `cards` добавляется необязательное поле `icon TEXT` с эмодзи-маркером;
- в диалоге создания материала появляется необязательный шаг выбора стикера, его можно пропустить;
- при пустом `icon` строка материала рендерится без маркера, выравнивание не ломается;
- рендер подставляет `icon` как есть и никогда не выводит цвет по знаку изменения — иначе
 пользователь начнёт читать в стикере смысл, которого в нём нет.

Ограничение на значение: одна графема из белого списка эмодзи. Произвольный текст в это поле
не допускается, иначе он попадёт в вывод как часть названия и исказит верстку.

### C-21. Формат чисел в вёрстке расходится с принятым **[РЕШЕНО]**

**Проблема.** В образце `1.000.327р`: точки как разделитель разрядов и строчная `р`. У материалов
при этом `124.276₽` — символ рубля. Внутри одного макета два формата.

**Решение.** Остаётся принятый ранее формат (C-5): узкий пробел U+202F как разделитель разрядов,
символ `₽`, копейки опускаются при `.00`, проценты — 2 знака `ROUND_HALF_UP`. Точка как разделитель
разрядов отклоняется: в русской типографике она конфликтует с десятичным разделителем и создаёт
риск прочитать `1.000` как одну тысячную. Если предпочтение принципиально — вопрос переоткрывается.

### C-22. Сходимость строк экрана и дневного P&L **[РЕШЕНО 24.08.2026]**

**Проблема.** `Σ CardChange = Cap(D) − Cap(prev)` верно только при неизменном множестве карт
в scope. Создание или удаление материала даёт невязку, а формулировка «сумма изменений равна
дневному P&L» верна ещё уже.

**Решение.** Тождество капитала дописано членами входа и выхода (`financial-model.md` §5.6,
PT-08). Следствие для прибыли: дневной P&L равен сумме изменений минус остатки
`TRANSFERRED` и `LOST`. Создание и пополнение равенство **сохраняют**: `capital_in` ровно
компенсирует рост капитала. Равенство на главном экране оговорено как случай дня без
перевода остатка и потери.

### C-26. Пополнение существующего материала **[РЕШЕНО 24.08.2026, рабочая модель]**

**Проблема.** C-7 больше не действует: нужна операция, которая увеличивает баланс карты
и не создаёт прибыли. На (карта, дата) по-прежнему одна актуальная запись (FR-3.5), поэтому
в один день можно и обновить баланс, и пополнить ту же карту — два смысла в одной строке.

**Почему нельзя «просто ввести новый баланс и спросить, прибыль это или пополнение».**
Это вернёт двусмысленность C-17.1 на каждое изменение. Две разные кнопки фиксируют намерение
до ввода числа.

**Решение.** На записи баланса хранится поле `capital_in` — часть этой суммы, пришедшая
извне. Потоки депозитов больше не выводятся из `initial_kind`, а читаются с актуальных записей:

```
Deposit за дату D = Σ capital_in актуальных записей с effective_date = D
```

Семантика операций:

| Действие | Что вводит пользователь | Новый `amount` | Поток на записи |
|---|---|---|---|
| Создание материала | текущий баланс `X` | `X` | `capital_in = X` |
| Обновление баланса | текущий баланс `Y` | `Y` | потоки без изменения (`0`/`0`, если первая запись за день) |
| Пополнение | новый баланс `Y >` текущего | `Y` | `capital_in += Y − текущий` |
| Трата | новый баланс `Y <` текущего | `Y` | `capital_out += текущий − Y` |

Одна запись на день, композиция сохраняет оба смысла. Пример: было 80 000; обновление
до 85 000 (прибыль 5 000); затем пополнение, ввод 95 000. Итог: `amount = 95 000`,
`capital_in = 10 000`, `PnL = 95 000 − 80 000 − 10 000 = 5 000`.

Пополнение и обновление выглядят одинаково (оба просят «какой баланс сейчас»), но это
разные кнопки: разница при обновлении — прибыль, разница при пополнении — депозит.
`Y ≤ текущий` в пополнении отклоняется — уменьшение баланса это расход, не пополнение.

Относительный ввод `+500` в любом диалоге по-прежнему запрещён (C-10): везде вводится
абсолютный баланс, как на карте.

Теорема T-10: пополнение (`Y >` текущего) не меняет P&L. Матрица: FT-27, FT-28, PT-10.

### C-27. Заморозка материала **[РЕШЕНО 24.08.2026, рабочая модель]**

**Проблема.** Заказчик описал «расход» как блок материала: выбранная карта уходит
в отдельную графу «заморожено». В модели такого состояния не было: карта либо в scope,
либо архивна. Архив необратим (C-9) и ставит вопрос о судьбе остатка — это не временный блок.

**Решение.** Третье состояние: `frozen`. Это не архив и не расход денег.

- Деньги остаются в общем капитале. `Cap` не меняется, потока нет, P&L = 0 (T-11).
- Главный экран делит капитал: «в работе» + «заморожено» = всего (T-6).
- Заморозка обратима: разморозка возвращает материал в оборот. История заморозок
  не ведётся — флаг текущий. Прошлые даты в отчёте видят полный капитал, без ретроспективы
  «что было заморожено 10 августа».
- Заморозка всей карты, не части суммы. Частичная заморозка потребовала бы второго
  баланса на одной карте и сломала LOCF.
- В проход «обновить все» замороженные не входят. С карточки замороженного материала
  доступны разморозка и обновление одной.
- Пополнение замороженного запрещено (FR-8.5).
- Кнопка называется «Расход». Под ней два действия: заблокировать материал и потратить/вывести
  без удаления (C-30). Настоящее удаление карты остаётся в настройках (C-17).

Поля: `cards.frozen_on DATE`, `cards.frozen_at TIMESTAMPTZ`. Оба NULL или оба NOT NULL.
Заморозить можно только неархивную карту. Имя по-прежнему уникально среди неархивных,
включая замороженные (C-6).

Теорема T-11: заморозка и разморозка не меняют `Cap` и `PnL`. Матрица: FT-29, PT-11.

### C-28. Главное меню под четыре действия учёта **[РЕШЕНО 24.08.2026]**

**Проблема.** Набор кнопок C-19 (обновить / добавить / удалить / настройки) не покрывает
пополнение существующего материала и заморозку. «Удалить» — редкое действие с тремя
ветвями судьбы остатка, ему не место на каждом экране рядом с ежедневными операциями.

**Решение.** Главный экран:

```
[🔄 Обновить балансы]
[➕ Пополнить]
[❄️ Расход]
[⚙️ Настройки]
```

`Пополнить` → добавить материал | пополнить существующий (ввод нового баланса).
`Расход` → заблокировать материал | потратить/вывести без удаления.
`Удалить материал` уходит в настройки рядом с архивом, переименованием, стикером и Excel.

Это не выкидывает C-17: диалог судьбы остатка жив, меняется только точка входа.
C-19 остаётся в силе как принцип двухуровневого меню.

### C-29. Тип начального баланса `PROFIT` убран **[РЕШЕНО 24.08.2026]**

**Проблема.** FR-2.2/FR-2.4 спрашивали при создании: «просто баланс» или «это прибыль».
Заказчик 24.08.2026: сумма при создании карты **никогда** не чистый плюс. Прибыль —
только дельта обновления (80к → 90к).

**Решение.** Вопрос при создании не задаётся. Каждая новая карта пишет `capital_in = amount`.
ENUM `initial_balance_kind` и поле `cards.initial_kind` удаляются — реализации ещё нет,
истории мигрировать нечего. Состояние FSM `CardCreateKind` не создаётся.

Сценарии П-3, П-7, FT-07b, FT-18 снимаются. Первая карта даёт P&L = 0 и депозит,
а не «доходность не определена из-за нулевой базы». C-2 (процент при базе ≤ 0) остаётся:
все карты в нуле по-прежнему возможны.

При добавлении карты с уже лежащими деньгами создавать как есть. Задним числом выделять
из стартового остатка «уже заработанное» не нужно: заказчик подтвердил это 24.08.2026.

### C-30. Трата без удаления материала **[РЕШЕНО 24.08.2026]**

**Проблема.** «Расход» в исходном описании был только блоком материала. Заказчик уточнил:
нужен и вариант «потратил / вывел», при котором карта остаётся. Удаление с «вывел» (C-17)
для этого слишком тяжелое: история уходит в архив, имя освобождается, обратного хода нет.

**Решение.** Вторая ветка `[❄️ Расход]`:

```
Расход
[❄️ Заблокировать материал]
[💸 Потратил / вывел]
[◀️ Назад]
```

Трата просит новый баланс `Y <` текущего — то же число, что на карте после списания.
`Δ = текущий − Y` пишется в `capital_out`. Капитал падает на `Δ`, поток `−Δ`, P&L = 0 (T-12).

Это симметрия пополнения: обе операции вводят абсолютный баланс, знак разницы задаёт кнопка.
Обновление баланса при падении `80к → 70к` было бы убытком; расход при том же вводе — вывод.

Карта не архивируется при `Y = 0`. Пустой материал дальше можно удалить из настроек.

Теорема T-12: трата не меняет P&L. Матрица: FT-30, PT-12.
