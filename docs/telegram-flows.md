# izicrm — Telegram: экраны и state machine

Handlers не содержат бизнес-логики (FR-6.3). Все многошаговые сценарии — явная state machine (FR-6.4).

---

## 1. Главный экран

Вёрстка задана заказчиком 23.08.2026 и заменяет макет §10 исходных требований.
Числа в присланном образце были черновыми — разбор в §1.2, скорректированная версия в §1.1.

### 1.1. Целевой вид

```
Общий баланс: 1 000 327 ₽

Сегодня        [+327 ₽ / +0.03%]
Август         [+10 562 ₽ / +1.07%]

Материал:

🟢 Сбер 7121*    124 276 ₽
                 [+200 ₽ / +0.16%]

🔴 Альфа 7131*   318 861 ₽
                 [+127 ₽ / +0.04%]

🔵 Втб 0134*     557 190 ₽
                 [+0 ₽ / 0.00%]

[🔄 Обновить балансы]
[➕ Добавить материал]
[🗑 Удалить материал]
[⚙️ Настройки]
```

Числа выше согласованы между собой и удовлетворяют инвариантам модели:

- `124 276 + 318 861 + 557 190 = 1 000 327` — сумма материалов равна общему балансу (T-6)
- `200 + 127 + 0 = 327` — сумма изменений равна дневному P&L (§5.6 модели)
- `327 / 1 000 000 = 0.0327%` → `0.03%` при `ROUND_HALF_UP`
- `10 562 / 989 765 = 1.0671%` → `1.07%`

### 1.2. Разбор чисел присланного образца

Зафиксировано для истории: в образце ни одна из четырёх групп чисел не сходилась.
Это не критика — образец задавал вёрстку. Но в реализации такие значения появиться не могут,
и каждый пункт закрыт тестом.

| Что в образце | Проблема | Тест |
|---|---|---|
| Материалы `124 276 + 318 861 + 678 146 = 1 121 283`, а показано `1 000 327` | Расхождение `120 956 ₽`: сумма материалов не равна общему балансу | UI-01, T-6 |
| `Сегодня +327 ₽ / +2.56%` | При базе `1 000 000` процент равен `0.0327%`. Для `2.56%` база должна быть `12 773 ₽` — это не капитал | UI-14 |
| `Август +10 562 ₽ / +12.2%` | При базе `989 765` процент равен `1.07%`. Для `12.2%` база должна быть `86 574 ₽` | UI-14 |
| У всех трёх материалов одинаковая дельта `+124 244 / +110%` | Дельты не могут совпадать при разных балансах. Восстановленные предыдущие значения дают `388 262%`, `64%` и `22%` — ни одно не равно `110%`. Сумма дельт `372 732 ₽` превышает дневную прибыль `327 ₽` в 1 140 раз | UI-01, PT-08 |

### 1.3. Правила отображения

| Элемент | Правило |
|---|---|
| Заголовок дневного блока | `Сегодня`, если обновление было сегодня; иначе фактическая дата последнего обновления (C-14) |
| Интервал > 1 дня | Добавляется `за N дней` (§5.2 модели) |
| Проценты | 2 знака, `ROUND_HALF_UP` (C-5) |
| Разделитель разрядов | Узкий пробел U+202F, символ `₽`. В образце были `1.000.327р` — точки как разделитель и `р` вместо `₽`; см. C-21 |
| Много материалов | Пагинация при превышении лимита 4096 символов |

Состояния значений:

| Ситуация | Отображение |
|---|---|
| Нет предыдущего дня | `—` вместо P&L и процента (FR-5.6) |
| База процента ≤ 0 | `+30 000 ₽ (—)` (C-2) |
| Нет материалов | Онбординг: `Пока нет ни одного материала` + `[➕ Добавить материал]` |
| Все материалы архивированы | `0 ₽`, P&L `—` |
| Материал создан после `prev` | `новый` вместо изменения (§5.6 модели) |

### 1.4. Словарь интерфейса

Термины интерфейса и кода расходятся сознательно (C-18). Перевод живёт только
в `interface/telegram/views` — ниже слоя `interface` слово «материал» не встречается.

| В интерфейсе | В коде и БД |
|---|---|
| материал | `Card`, `cards`, `cardId` |
| список материалов | `listUserCards` |
| удалить материал | архивирование, `archiveUserCard` |
| стикер материала | `cards.icon` |

Правило: если новый текст экрана требует слова «карта» — это ошибка перевода, а не
исключение. Обратное тоже верно: `Material` в именах типов и таблиц не появляется.

### 1.5. Нерешённые вопросы по этому экрану

Влияют на реализацию, ответы нужны до этапа UI: C-17 (что делать с остатком при удалении
материала — прочтение «плюс/минус» не определено) и C-19 (куда делся Excel-отчёт).
Полные формулировки — `docs/requirements.md` §4.

Закрыты 23.08.2026: C-18 (термин «материал» — см. §1.4), C-20 (стикеры декоративные),

## 2. Состояния FSM

Размеченное объединение. Payload валидируется Zod при чтении из `dialog_states`.
**Денежные суммы в payload — строки** (ADR-005).

```ts
type DialogState =
  | { t: 'Idle' }
  | { t: 'CardCreateName' }
  | { t: 'CardCreateBalance';   name: string }
  | { t: 'CardCreateKind';      name: string; amount: string }
  | { t: 'CardCreateIcon';      name: string; amount: string; kind: InitialBalanceKind }
  | { t: 'CardRenameName';      cardId: CardId }
  | { t: 'BalanceUpdateAmount'; queue: CardId[]; index: number;
                                businessDate: BusinessDate; done: UpdatedCard[] }
  | { t: 'ArchiveConfirm';      cardId: CardId }
  | { t: 'ArchiveDisposition';  cardId: CardId; lastBalance: string }
  | { t: 'ArchiveTarget';       cardId: CardId; amount: string }
  | { t: 'ReportBuilding' };
```

Один тип состояния `BalanceUpdateAmount` обслуживает и одну карту, и все: разница только
в длине `queue` (FR-4.3). Второй сценарий не пишется.

`CardCreateIcon` — выбор декоративного стикера (C-20), необязательный шаг. Он последний, поэтому
карта создаётся одной записью после него: `icon` не требует отдельного `UPDATE` сразу после
`INSERT`. Стикер меняется позже наравне с названием — он не финансовое данное, и запрет
на изменение (правило 5) к нему не относится.

`businessDate` фиксируется при входе в состояние и не пересчитывается на последующих шагах —
иначе диалог, начатый 31 августа в 23:59, разложил бы записи по двум месяцам (C-11).

## 3. Таблица переходов

Функция перехода чистая: `reduce(state, event, ctx) → { next, effects }`. Тестируется без Telegram.

> Сами переходы вёрсткой от 23.08.2026 не затронуты — изменился только набор точек входа с
> главного экрана. Коды `cb:card_add`, `cb:card_archive`, `cb:report` и экраны списка и
> переименования будут приведены к новому набору кнопок после ответов на C-17 и C-19.
> Состояние `ArchiveConfirm` обслуживает кнопку `[🗑 Удалить материал]`: действие остаётся
> архивированием (C-17). Ветки `ArchiveDisposition` ниже соответствуют формулировкам C-3
> и будут переписаны, когда решится C-17.1 — уточнение «записать сумму как плюс / как минус».
> Возможное третье значение `archive_reason = LOST` (остаток объявлен убытком) в схеме пока
> не заведено намеренно: его существование зависит от того же ответа.

| Состояние | Событие | Переход | Эффект |
|---|---|---|---|
| `Idle` | `/start`, `cb:home` | `Idle` | Показать главный экран |
| `Idle` | `cb:card_add` | `CardCreateName` | Запросить название |
| `CardCreateName` | текст | `CardCreateBalance` | Проверить название: непустое, ≤ 64, нет активного дубля |
| `CardCreateName` | текст, дубль | `CardCreateName` | «Карта с таким названием уже есть» |
| `CardCreateBalance` | текст | `CardCreateKind` | Разобрать сумму; спросить тип |
| `CardCreateBalance` | текст, невалиден | `CardCreateBalance` | Показать правила ввода |
| `CardCreateKind` | `cb:kind_balance` | `CardCreateIcon` | Запомнить `kind = BALANCE`; предложить стикер |
| `CardCreateKind` | `cb:kind_profit` | `CardCreateIcon` | Запомнить `kind = PROFIT`; предложить стикер |
| `CardCreateIcon` | `cb:icon:<n>` | `Idle` | Создать карту со стикером; `BALANCE` → депозит, `PROFIT` → без потока |
| `CardCreateIcon` | `cb:skip` | `Idle` | Создать карту с `icon = NULL` |
| `CardCreateIcon` | `cb:icon:<n>`, `n` вне белого списка | `CardCreateIcon` | Игнорировать: `callback_data` недоверенный |
| `Idle` | `cb:upd_all` | `BalanceUpdateAmount` | `queue` = активные карты по алфавиту; `businessDate` = сегодня |
| `Idle` | `cb:upd_one:<id>` | `BalanceUpdateAmount` | `queue` = `[id]` после проверки владения |
| `BalanceUpdateAmount` | текст | тот же / `Idle` | Записать баланс; `index++`; при исчерпании — итог и `Idle` |
| `BalanceUpdateAmount` | текст, невалиден | тот же | Показать правила; `index` не меняется |
| `BalanceUpdateAmount` | `cb:skip` | тот же / `Idle` | Пропустить карту без записи (LOCF сохраняет прежний баланс) |
| `Idle` | `cb:card_rename:<id>` | `CardRenameName` | Запросить новое название |
| `CardRenameName` | текст | `Idle` | Переименовать; уникальность проверяется заново |
| `Idle` | `cb:card_archive:<id>` | `ArchiveConfirm` | Спросить подтверждение |
| `ArchiveConfirm` | `cb:yes`, остаток = 0 | `Idle` | Архивировать, `reason = WITHDRAWN`, поток 0 |
| `ArchiveConfirm` | `cb:yes`, остаток ≠ 0 | `ArchiveDisposition` | Спросить судьбу остатка (C-3) |
| `ArchiveDisposition` | `cb:withdrawn` | `Idle` | Архивировать; `WITHDRAWAL` на остаток |
| `ArchiveDisposition` | `cb:transferred` | `ArchiveTarget` | Показать список карт-получателей |
| `ArchiveTarget` | `cb:target:<id>` | `Idle` | Транзакция: обнулить источник, прибавить остаток получателю, архивировать `TRANSFERRED`, потока нет |
| `Idle` | `cb:report` | `ReportBuilding` | Rate limit; сформировать и отправить файл |
| `ReportBuilding` | завершение | `Idle` | Отправить документ |
| любое | `cb:cancel` | `Idle` | Сбросить состояние, показать главный экран |
| любое | истёк `expires_at` | `Idle` | «Диалог отменён из-за неактивности», показать главный экран |

Guard-и, выполняемые перед **каждым** переходом, затрагивающим карту:

1. Карта существует и принадлежит `userId` (`getUserCard(userId, cardId)`).
2. Карта активна, если операция требует активной.
3. `state_rev` из `callback_data` совпадает с текущим — иначе `StaleCallbackError`.

Guard-и — единственное место, где проверяется владение. Они не полагаются на то, что кнопка
была отрисована для этого пользователя (FR-1.5).

## 4. Экраны диалогов

### Создание карты

```
Введите название карты:                        [Отмена]
→ Сбер1

Сбер1
Введите текущий баланс:                        [Отмена]
→ 10000

Сбер1 · 10 000 ₽

Это:
[📊 Просто текущий баланс]
[📈 Это прибыль]
```

Пояснение под кнопками — оно предотвращает главную содержательную ошибку пользователя:

```
Просто текущий баланс — точка отсчёта, прибылью не считается.
Это прибыль — сумма попадёт в прибыль за сегодня.
```

### Обновление балансов

```
Сбер1  (1 из 3)
Предыдущий баланс: 1 000 ₽

Введите текущий баланс:
[⏭ Пропустить]  [Отмена]
```

После прохода:

```
Обновлено 3 карты · 20 августа

116 000 ₽
+1 200 ₽ (+1.05%)

Сбер1     10 500 ₽   +500 ₽
Сбер2     21 300 ₽   +700 ₽
Тинькофф   7 800 ₽     +0 ₽
```

При пропуске части карт итог включает строку `Пропущено: 1` — не предупреждение, а факт.

### Архивирование с ненулевым остатком (C-3)

```
Архивировать «Сбер2»?
Текущий баланс: 20 000 ₽

История карты сохранится и останется в отчётах.
Куда делись эти деньги?

[💸 Выведены со счёта]
[↔️ Переведены на другую карту]
[Отмена]
```

Второй вариант ведёт к выбору карты-получателя и в одной транзакции переносит остаток.
Оба варианта дают `P&L = 0` (теорема T-3). Без этого вопроса система не смогла бы отличить
вывод от внутреннего перевода и показала бы фантомный убыток или фантомную прибыль.

## 5. Протокол `callback_data`

Формат: `v1:<action>:<id>:<rev>`, лимит Telegram — 64 байта.

| Часть | Назначение |
|---|---|
| `v1` | Версия протокола; неизвестная версия → перерисовка экрана |
| `action` | Короткий код действия |
| `id` | ID сущности, **недоверенный**: всегда перепроверяется по `user_id` |
| `rev` | `state_rev` пользователя на момент отрисовки кнопки |

`rev` решает конкретную проблему: пользователь может нажать кнопку в старом сообщении,
пролистав историю чата. Без проверки ревизии это привело бы к повторной записи баланса или
к операции над уже архивированной картой. Несовпадение `rev` → «Кнопка устарела» + перерисовка.

Идемпотентность на уровне доставки — `processed_updates(update_id)` (ADR-009): повторная
доставка апдейта Telegram не создаёт вторую запись.

## 6. Ошибки и граничные ситуации

| Ситуация | Поведение |
|---|---|
| Невалидная сумма | Правила ввода, состояние не меняется (FR-6.5) |
| Более 2 знаков после запятой | «Копейки — не более двух знаков». Без молчаливого округления (C-12) |
| Сумма вне `±10^15` | «Слишком большое значение» |
| Дубль названия | «Карта с таким названием уже есть» |
| Чужой `card_id` в callback | Нейтральное «Карта не найдена» + запись в лог безопасности |
| Карта архивирована в процессе прохода | Guard пропускает её, проход продолжается |
| Нет активных карт при `cb:upd_all` | «Нет активных карт» + `[➕ Добавить карту]` |
| Диалог неактивен > 30 минут | Сброс в `Idle` при следующем действии |
| Повторный `cb:report` | Rate limit: не чаще 1 раза в минуту |
| Пользователь заблокировал бота (403) | Отметить `blocked_at`, прекратить отправку |
| Сообщение > 4096 символов | Пагинация списка карт |
